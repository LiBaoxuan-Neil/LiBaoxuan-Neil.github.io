OpenAI Chat Completions SSE API 流式响应

深入 OpenAI Chat Completions：从 ChatCompletionCreateParams 到 SSE 流式响应

Posted by LiBaoxuan on Monday, August 31, 2026
9 分钟阅读

当你第一次用代码调用 gpt-4o 时，最先遇到的往往不是一个"模型"，而是一长串需要填对的参数：模型 ID 填什么？消息数组怎么组织？要不要开流式传输？这些问题的答案，都藏在 OpenAI 官方 SDK 的核心类型 ChatCompletionCreateParams 和它背后那个最常被调用的接口 /chat/completions 之中。

这篇文章想做一件事：把"怎么正确地向 OpenAI 发一条聊天请求"这件事，从参数契约、接口规范、流式协议到连接关闭，串成一条完整的链路讲清楚。无论你用的是 TypeScript、Python 还是 Java，读完都应该能明白每行代码背后在约束什么。

一、ChatCompletionCreateParams：类型安全的请求参数契约

1.1 它到底是什么

ChatCompletionCreateParams 是 OpenAI API 官方 SDK 中的一个核心类型（或类），用于规范地构建调用聊天补全（Chat Completions）接口（/chat/completions）的请求参数。

简单来说，当你想通过代码调用像 gpt-4o 这样的模型时，就需要创建一个该类型的对象，并填入所有必要的参数。

1.2 核心作用：类型安全与参数规范

它的主要作用是类型安全和参数规范。它明确定义了哪些参数是必需的、哪些是可选的，以及每个参数的类型和取值范围。这能帮助你在编写代码时避免错误，比如忘记提供 messages 或 model 字段。

1.3 跨语言的表现形式

这个契约在不同语言里的"长相"并不一样：

  • TypeScript：被定义为一个联合类型（Union Type），由 ChatCompletionCreateParamsNonStreaming（非流式）和 ChatCompletionCreateParamsStreaming（流式）组成。
  • Python / Java 等：通常表现为一个类（Class）或类型提示（TypedDict）。

也就是说，无论用哪种语言，你填的每一个字段、每一种取值，最终都要满足同一份"契约"。

1.4 关键参数解析

ChatCompletionCreateParams 包含众多参数，以下是最核心和常用的一些：

参数名类型是否必需描述
messagesArray<Message>是对话消息列表，是模型生成回复的依据。
modelstring是要使用的模型 ID，例如 "gpt-4o"、"gpt-3.5-turbo" 等。
streamboolean否是否启用流式传输，即让模型逐词生成回复。
temperaturenumber否控制生成文本的随机性，取值范围 0–2，值越低越确定和保守。
max_completion_tokensnumber否生成回复的最大 token 数量，用于控制输出长度。
toolsArray<Tool>否定义模型可以调用的工具或函数列表，用于实现 Function Calling。
response_formatobject否指定模型输出的格式，如纯文本（text）或结构化 JSON（json_object）。
frequency_penaltynumber否根据 token 在文本中出现的频率进行惩罚，取值范围 -2.0 到 2.0，用于减少重复。

可以看到，messages 和 model 是两个"没有它们请求就不成立"的字段，其余参数则是用来精细控制模型行为的旋钮。

二、/chat/completions：驱动聊天模型的核心接口

ChatCompletionCreateParams 只是"请求该怎么填"的定义；真正接收请求、返回回复的，是 OpenAI API 最核心的接口 /chat/completions。

2.1 接口核心信息

  • 接口名称：Create chat completion
  • 功能描述：为给定的聊天对话创建模型回复
  • 请求路径：POST /v1/chat/completions
  • 完整 URL：https://api.openai.com/v1/chat/completions
  • 返回结果：一个 ChatCompletion 对象；如果请求中设置了 stream: true，则返回一个流式的 ChatCompletionChunk 对象序列

简单来说，你向这个接口发送一个对话历史（messages），模型会根据这些信息生成并返回回复。

2.2 请求头（Headers）

在发起请求时，HTTP 头部需要包含以下信息：

参数名是否必需描述
Content-Type是必须为 application/json
Authorization是你的 API 密钥，格式为 Bearer YOUR_API_KEY

2.3 核心请求体参数（Body Parameters）

请求体是一个 JSON 对象，包含了控制模型生成的所有参数。核心字段与 ChatCompletionCreateParams 高度对应：

参数名类型是否必需描述
messagesarray是对话消息列表。每个消息对象都包含 role（如 system、user、assistant）和 content（消息内容）。
modelstring是要使用的模型 ID，例如 gpt-4o、gpt-3.5-turbo。
streamboolean否是否启用流式传输。若为 true，模型会逐词（或逐片段）生成回复。
temperaturenumber否控制生成文本的随机性，取值范围 0–2。值越低，输出越确定和保守。
max_completion_tokensnumber否生成回复的最大 token 数量，用于控制输出长度。
toolsarray否定义模型可以调用的工具或函数列表，用于实现 Function Calling。
response_formatobject否指定模型输出的格式，如 text 或 json_object。
frequency_penaltynumber否根据 token 在文本中出现的频率进行惩罚，取值范围 -2.0 到 2.0，用于减少重复。

2.4 响应格式（Response）

一个典型的非流式响应（stream: false）是一个 ChatCompletion 对象：

{
  "id": "chatcmpl-abc123",        // 本次生成的唯一ID
  "object": "chat.completion",    // 对象类型
  "created": 1677858242,          // 生成时的Unix时间戳
  "model": "gpt-4o",              // 使用的模型
  "choices": [                    // 生成的回复选项列表
    {
      "index": 0,                 // 选项索引
      "message": {                // 模型生成的回复消息
        "role": "assistant",
        "content": "你好！今天有什么可以帮你的？"
      },
      "finish_reason": "stop"     // 生成结束的原因，如 "stop", "length" 等
    }
  ],
  "usage": {                      // Token使用情况统计
    "prompt_tokens": 10,
    "completion_tokens": 20,
    "total_tokens": 30
  }
}

2.5 请求示例（cURL）

curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{
    "model": "gpt-4o",
    "messages": [
      {"role": "system", "content": "你是一个乐于助人的助手。"},
      {"role": "user", "content": "你好！"}
    ]
  }'

三、流式响应与 SSE 协议

当你在调用 /chat/completions 接口时设置 stream: true，使用的就是 Server-Sent Events (SSE) 协议。

3.1 为什么是 SSE

SSE 是一种基于 HTTP 的轻量级实时通信协议，非常适合文本流式传输。它恰好契合了大模型生成内容的场景：客户端发送一次请求后，只需持续接收模型生成的文本片段即可。

3.2 SSE 协议的核心特征

  • 基于 HTTP，简单易用：SSE 复用了标准的 HTTP 协议，无需像 WebSocket 那样进行协议升级，开发和调试都更为方便。
  • 服务端单向推送：数据只能由服务器单向推送给客户端。这恰好符合大模型生成内容的场景。
  • 长连接：客户端发起请求后，服务器会保持这个 HTTP 连接不断开，用于持续发送数据。
  • 标准 MIME 类型：SSE 数据流使用特定的 MIME 类型 text/event-stream 进行传输。

3.3 SSE 数据流的格式

启用 stream: true 后，服务器通过 SSE 格式返回数据，基本结构如下：

  1. 每个数据块以 data: 前缀开头，后面跟着一个 JSON 字符串。
  2. JSON 对象包含了模型生成的文本片段（通常在 choices[0].delta.content 字段中）。
  3. 每个数据块之间用空行分隔。
  4. 流以 data: [DONE] 标记结束。

一个典型的 SSE 响应片段：

data: {"id":"chatcmpl-123","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"你好"},"finish_reason":null}]}

data: {"id":"chatcmpl-123","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"，世界"},"finish_reason":null}]}

data: [DONE]

3.4 与 WebSocket 的对比

维度SSE (Server-Sent Events)WebSocket
通信方向基于 HTTP 的单向通信双向、全双工通信
适用场景服务器向客户端推送数据（如文本生成）客户端与服务器频繁互动（如在线游戏、实时聊天）

对于调用大模型 API 生成文本，单向的 SSE 是更简单、更高效的选择。

四、data: [DONE] 与连接关闭：健壮实现的标准做法

这里有一个容易被忽略、也容易踩坑的细节。

4.1 “关闭"发生在应用层，而非协议层

data: [DONE] 输出后，连接通常会被关闭，但这个"关闭"行为发生在应用层面，而不是由 SSE 协议自身强制规定的。

4.2 连接关闭的两种方式

  1. 服务端主动关闭（常规做法） 按照 OpenAI 的协议和大多数网关的实现，在发送完 data: [DONE] 这个终止信号后，服务端会主动关闭底层的 TCP 连接。这是最标准、最常见的做法。例如，Ferro Labs AI Gateway 的文档就明确指出，在写入 [DONE] 标记后会"关闭连接”。

  2. 客户端主动关闭（最佳实践） 出于健壮性考虑，最佳实践是让客户端在收到 [DONE] 信号后，主动关闭连接。这样做可以避免因网络问题或服务端未及时断开而导致的资源浪费或程序"挂起"。

4.3 为什么需要客户端主动关闭

服务端在发送 [DONE] 后立即关闭连接是最理想的，但在实际网络环境中，中间可能经过负载均衡器、代理服务器等，它们有可能在转发 [DONE] 后依然保持着连接。

如果客户端只是被动等待服务端关闭，就可能出现无限等待的情况。因此，官方 SDK 和成熟的客户端代码都会在解析到 [DONE] 这个特定字符串后，主动停止读取并关闭连接。

4.4 一个完整的交互流程

  1. 客户端发起请求，设置 "stream": true。
  2. 服务端以 SSE 格式持续推送数据块（data: {...}\n\n）。
  3. 模型生成完毕，服务端发送最后一个数据块：data: [DONE]\n\n。
  4. 服务端通常会主动关闭底层的 TCP 连接。
  5. 客户端在解析到 [DONE] 后，也应主动停止读取并关闭连接——这是一个健壮实现的标准做法。

总的来说，data: [DONE] 是应用层定义的"结束"信号，收到它意味着本次请求的数据已经全部传输完毕。虽然服务端通常会随之关闭连接，但最可靠的做法是客户端在收到此信号后主动关闭自己的那端连接。

五、总结

把整条链路串起来看：

  • ChatCompletionCreateParams 是 OpenAI SDK 为开发者提供的一个标准化"契约"，它精确地定义了与 AI 模型交互所需的所有参数，确保了 API 调用的准确性和高效性——在使用任何语言的 OpenAI 官方 SDK 时，你都会频繁地用到它。
  • /chat/completions 是驱动 OpenAI 聊天模型的核心接口，通过结构化的 messages 数组传入对话历史，并用丰富的参数来控制模型的输出。
  • SSE + data: [DONE] 则是流式场景下"如何让回复逐字送达、又如何让连接干净收尾"的答案。

理解这三层——参数契约、接口规范、流式协议——你就掌握了用代码和 GPT 类模型对话的基本功。想进一步深入，可以参考 OpenAI 的官方文档或 MDN 上关于 SSE 的教程。
