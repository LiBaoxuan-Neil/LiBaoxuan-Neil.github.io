深入 Dapr 服务调用：从 invoke API 到 mTLS gRPC 通道的完整链路

基于 dapr/dapr 源码逐层剖析 Service Invocation 的实现原理

Posted by LiBaoxuan on Tuesday, September 8, 2026

本文所有结论均基于 dapr/dapr 仓库 commit bbb49bc81a9f3d91cf3b76bb35c868a389d3972e（2026-06-02）的实际源码。行号以该 commit 为准。涉及 components-contrib 的部分已单独标注。

一、背景：服务调用要解决的到底是什么问题

在微服务架构里，“A 服务调用 B 服务"这件看似简单的事，实际上要同时回答五个问题：

  1. 服务发现：B 在哪里？有几个实例？实例上下线了怎么办？
  2. 协议标准化：A 用 HTTP、B 用 gRPC 怎么互通？
  3. 安全：怎么保证链路加密，怎么确认"你确实是 B 而不是伪装的 B”，怎么做方法级授权？
  4. 可靠性：网络抖动、实例重启、证书轮换导致的瞬时失败怎么办？
  5. 可观测：一次跨三个服务的调用，出问题时怎么定位是哪一跳慢了？

传统做法是在每个服务里塞进 SDK：注册中心客户端、负载均衡器、重试库、熔断器、mTLS 配置、tracing 埋点……这些代码与业务无关，却要在每种语言里重复实现一遍，且升级极其痛苦。

Dapr 的答案是 sidecar 反向代理：应用只跟本地 sidecar 说话，跨网络的脏活全部下沉到 sidecar。Dapr 官方文档对这条链路的描述是：

“All calls between Dapr sidecars go over gRPC for performance. Only calls between services and Dapr sidecars can be either HTTP or gRPC.”

这句话是理解整个实现的钥匙——应用与 sidecar 之间是 HTTP 或 gRPC 二选一，而 sidecar 与 sidecar 之间永远只有 gRPC。因此 Dapr 内部只需要维护一套传输实现，所有协议转换都发生在链路的两端。

本文就沿着这条链路，从 /v1.0/invoke 一路走到目标应用的 socket。

二、整体架构：一次调用的分层视角

先建立整体心智模型。以"App A 通过 HTTP 调用 App B"为例：

App A ──HTTP──▶ sidecar A ──gRPC(mTLS)──▶ sidecar B ──HTTP/gRPC──▶ App B

在 sidecar 内部，这条链路被拆成五个职责清晰的层次：

层次 位置 职责
入口层（API） pkg/api/http、pkg/api/grpc 协议适配、参数解析、构造内部请求对象
路由层 pkg/messaging/direct_messaging.go 服务发现、本地/远端判定
执行层 pkg/messaging/direct_messaging.go 重试、超时、错误分类、请求重放
传输层 pkg/api/grpc/manager、pkg/security 连接池、负载均衡、mTLS
交付层（目标侧） pkg/api/grpc/daprinternal.go、pkg/channel ACL 鉴权、转发到本地 App

而把这一切串起来的，只有一个极简接口（pkg/messaging/v1/messaging.go:20-23）：

// DirectMessaging is the API interface for invoking a remote app.
type DirectMessaging interface {
	Invoke(ctx context.Context, targetAppID string, req *InvokeMethodRequest) (*InvokeMethodResponse, error)
}

这是整个服务调用最重要的一个抽象。 HTTP 入口和 gRPC 入口都只持有这个接口，对后面发生的服务发现、重试、mTLS 一无所知。这种"一个窄接口切断所有耦合"的设计，是 Dapr 能同时支持 HTTP/gRPC 入口和多种托管平台的根本原因

。

三、入口层：HTTP 与 gRPC 如何汇聚到同一个点

3.1 HTTP 侧：一条路由兜住所有动词

Dapr 的 HTTP 服务调用只注册了一条 endpoint（pkg/api/http/directmessaging.go:74-95）：

func (a *api) constructDirectMessagingEndpoints() []endpoints.Endpoint {
	return []endpoints.Endpoint{
		{
			// No method is defined here to match any method
			Methods: []string{},
			Route:   "invoke/*",
			Version: apiVersionV1,
			Group: &endpoints.EndpointGroup{
				Name:                 endpoints.EndpointGroupServiceInvocation,
				Version:              endpoints.EndpointGroupVersion1,
				AppendSpanAttributes: appendDirectMessagingSpanAttributes,
				MethodName:           directMessagingMethodNameFn,
			},
			Handler: a.onDirectMessage,
			Settings: endpoints.EndpointSettings{
				Name:       "InvokeService",
				IsFallback: true,
			},
		},
	}
}

三个设计细节值得注意：

① Methods 为空 = 匹配任意方法。 在 pkg/api/http/server.go:461-484 的 handle 中，空 Methods 走 r.Handle(path, handler) 而非 r.Method(m, path, handler)。GET/POST/PUT/DELETE 不在路由层区分，全部落到同一个 handler。

② IsFallback: true 让它同时成为 NotFound 和 MethodNotAllowed 的处理器。 这正是 Dapr 支持"不改 URL，只加一个 dapr-app-id 头就能调用"的实现基础——任意路径都能命中。

③ 路径是 /v1.0/invoke/*（server.go:439 拼装为 "/" + e.Version + "/" + e.Route）。

目标应用的 ID 与方法名从三处解析（pkg/api/http/directmessaging.go:360-408）：

// findTargetIDAndMethod finds ID of the target service and method from the following three places:
// 1. HTTP header 'dapr-app-id' (path is method)
// 2. Basic auth header: `http://dapr-app-id:<service-id>@localhost:3500/<method>`
// 3. URL parameter: `http://localhost:3500/v1.0/invoke/<app-id>/method/<method>`

注意这里用的是解码后的 r.URL.Path 而非 RawPath（directmessaging.go:97-105），注释解释得很清楚：

// Use Path (decoded) rather than RawPath so that percent-encoded characters
// are resolved before method extraction. This ensures the method string
// used for ACL evaluation and dispatch is the decoded canonical form.

这是一个安全设计：先解码再提取方法名，保证"ACL 判定的字符串"与"实际派发的字符串"是同一个规范形式。否则 %2e%2e%2f 这类编码就能绕过基于路径的 ACL 匹配。这是典型的 canonicalization before validation（先规范化再校验）原则。

随后构造内部请求对象（directmessaging.go:137-160）：

req := invokev1.NewInvokeMethodRequest(invokeMethodName).
	WithHTTPExtension(verb, r.URL.RawQuery).
	WithRawData(r.Body).
	WithContentType(r.Header.Get("content-type")).
	// Save headers to internal metadata
	WithHTTPHeaders(r.Header).
	WithHTTPResponseWriter(w)
// For streaming requests (chunked transfer / unknown content length),
// disable replay to prevent buffering the entire body in memory.
if r.ContentLength < 0 {
	req.SetStreamingRequest()
}
if policyDef != nil {
	req.WithReplay(policyDef.HasRetries())
}
defer req.Close()

三个要点：r.Body 作为 io.Reader 直接传入（不落地内存）、query string 原样透传、以及 ContentLength < 0 时标记为流式请求（后面会讲为什么这会导致重试被禁用）。

3.2 gRPC 侧：三个 RPC 的分工

gRPC 侧有三个相关 RPC，容易混淆：

RPC 位置 用途 状态
InvokeService pkg/api/grpc/grpc.go:277 应用主动发起的调用 已标记 Deprecated
CallLocal pkg/api/grpc/daprinternal.go:44 sidecar → sidecar（一元） 内部
CallLocalStream pkg/api/grpc/daprinternal.go:85 sidecar → sidecar（流式） 内部，当前主路径

InvokeService 的实现里已经明确写着：

// Deprecated: Use proxy mode service invocation instead.
func (a *api) InvokeService(ctx context.Context, in *runtimev1pb.InvokeServiceRequest) (*commonv1pb.InvokeResponse, error) {
	if a.directMessaging == nil {
		return nil, messages.ErrDirectInvokeNotReady
	}
	if invokeServiceDeprecationNoticeShown.CompareAndSwap(false, true) {
		apiServerLogger.Warn("[DEPRECATION NOTICE] InvokeService is deprecated and will be removed in the future, please use proxy mode instead.")
	}

Dapr 正在把服务调用从"自定义 RPC + InvokeRequest 包装"迁移到"gRPC 透明代理"。 新模式下应用直接发自己的 proto 方法，daprd 通过 UnknownServiceHandler 接管不认识的方法并转发（pkg/api/grpc/server.go:357-359）：

if s.proxy != nil {
	opts = append(opts, grpcGo.UnknownServiceHandler(s.proxy.Handler()))
}

这样应用无需引入任何 Dapr SDK 或 Dapr 自定义的 proto。

3.3 汇聚点与内部请求对象

无论 HTTP 还是 gRPC，最终都构建同一个内部对象 InvokeMethodRequest（pkg/messaging/v1/invoke_method_request.go:37-49）：

type InvokeMethodRequest struct {
	replayableRequest

	r                  *internalv1pb.InternalInvokeRequest
	dataObject         any
	dataTypeURL        string
	httpResponseWriter http.ResponseWriter
	// streamingRequest is set when the request body is a stream that cannot be
	// replayed (e.g. chunked-transfer / unknown content-length).
	// When true, WithReplay becomes a no-op to prevent the entire body
	// from being buffered into memory for retry purposes.
	streamingRequest bool
}

其内部表示 InternalInvokeRequest（pkg/proto/internals/v1/service_invocation.pb.go:97-111）包含四个字段：Ver、Metadata、Message、Actor。

这里是最关键的设计决策之一：HTTP header 与 gRPC metadata 被统一成同一个 Metadata map[string]*ListStringValue。

func HTTPHeadersToInternalMetadata(header http.Header) map[string]*ListStringValue {
	internalMD := make(map[string]*ListStringValue, len(header))
	for key, val := range header {
		// Note: HTTP headers can never be binary (only gRPC supports binary headers)
		...
	}
	return internalMD
}

因为 HTTP header 是多值的，gRPC metadata 也是多值的，两者可以无损互转。这意味着sidecar ↔ sidecar 这一段完全不需要知道上游是 HTTP 还是 gRPC——它只搬运 Metadata + Message，到目标端再按需转回 HTTP header 或 gRPC metadata。这是"双协议支持"能保持低成本的根本原因。

四、路由层：从 appID 到一个 host:port

4.1 appID 与 namespace 的拆分

Dapr 的命名空间模型极其简单（pkg/messaging/direct_messaging.go:193-210）：

func (d *directMessaging) requestAppIDAndNamespace(targetAppID string) (string, string, error) {
	if targetAppID == "" {
		return "", "", errors.New("app id is empty")
	}
	// external invocation with targetAppID == baseURL
	if strings.HasPrefix(targetAppID, "http://") || strings.HasPrefix(targetAppID, "https://") {
		return targetAppID, "", nil
	}
	items := strings.Split(targetAppID, ".")
	switch len(items) {
	case 1:
		return targetAppID, d.namespace, nil
	case 2:
		return items[0], items[1], nil
	default:
		return "", "", fmt.Errorf("invalid app id %s", targetAppID)
	}
}

只支持 appID 或 appID.namespace 两种形式，超过两段直接报错。 不写 namespace 时取本 sidecar 的 namespace。

注意 http:// / https:// 前缀这个特例——它让 Dapr 能用同一套 API 调用非 Dapr 的外部 HTTP 服务（这也是 HTTPEndpoint CRD 的实现基础）。

4.2 getRemoteApp：三条分支与缓存

getRemoteApp（direct_messaging.go:607-685）是服务发现的入口：

switch {
case strings.HasPrefix(res.id, "http://") || strings.HasPrefix(res.id, "https://"):
	res.address = res.id
case d.isHTTPEndpoint(res.id):
	res.address = d.checkHTTPEndpoints(res.id)
default:
	request := nr.ResolveRequest{
		ID:        res.id,
		Namespace: res.namespace,
		Port:      d.grpcPort,
	}
	// ... 解析
}

解析分两条路径，取决于 resolver 是否实现了可选接口 ResolverMulti：

// If the component implements ResolverMulti, we can use caching
if d.resolverMulti != nil {
	var addresses nr.AddressList
	if d.resolverCache != nil {
		res.cacheKey = request.CacheKey()
		addresses, _ = d.resolverCache.Get(res.cacheKey)
		if len(addresses) > 0 {
			// Pick a random one
			res.address = addresses.Pick()
		}
	}
	if res.address == "" {
		addresses, err = d.resolverMulti.ResolveIDMulti(ctx, request)
		...
		res.address = addresses.Pick()
		if len(addresses) > 0 && res.cacheKey != "" {
			d.resolverCache.Set(res.cacheKey, addresses, resolverCacheTTL)
		}
	}
} else {
	err = backoff.Retry(func() error {
		var rerr error
		res.address, rerr = d.resolver.ResolveID(ctx, request)
		if rerr != nil {
			return backoff.Permanent(rerr)
		}
		if len(res.address) == 0 {
			return fmt.Errorf("resolver returned empty address for app id %s/%s", request.Namespace, request.ID)
		}
		return nil
	}, backoff.WithMaxRetries(
		backoff.WithContext(backoff.NewConstantBackOff(100*time.Millisecond), ctx),
		5),
	)
}

这里有三个值得学习的设计点：

① 用类型断言做能力探测。 dm.resolverMulti, _ = opts.Resolver.(nr.ResolverMulti)（direct_messaging.go:136）。老组件只实现 ResolveID 也能正常工作，新组件实现 ResolveIDMulti 就能获得多地址 + 缓存能力。这是 Go 里做"向后兼容的能力升级"的标准姿势。

② 缓存只在多地址场景下建立。 resolverCache 仅在 resolverMulti != nil 时才创建（direct_messaging.go:135-141），因为单地址 resolver（如 mDNS）内部已有自己的缓存，再套一层是浪费。

③ 重试策略区分错误类型。 resolver 返回的真实错误是 backoff.Permanent（不重试），只有"返回空地址"才重试。这个区分很精准——解析失败（配置错误、网络不通）重试没意义，而"暂时还没发现"重试是有意义的。

AddressList.Pick() 的实现也很有意思（components-contrib/nameresolution/nameresolution.go）：

func (a AddressList) Pick() string {
	l := len(a)
	switch l {
	case 0:
		return ""
	case 1:
		return a[0]
	default:
		// We use math/rand here as we are just picking a random address, so we don't need a CSPRNG
		//nolint:gosec
		return a[rand.Intn(l)]
	}
}

注意这是客户端随机选择，不是轮询。 配合下面的 dns:/// 与 gRPC 内置 round_robin，形成了两级负载均衡。

4.3 Name Resolution 的实现（注意：不在主仓库）

重要说明：dapr/dapr 主仓库中不包含任何 resolver 实现。核心接口与所有 resolver 都在 github.com/dapr/components-contrib（本文对应本地检出 commit 0d6569ac）。主仓库只保留注册表、装配点与上层集成。

接口定义（components-contrib/nameresolution/nameresolution.go:23-36）：

// Resolver is the interface of name resolver.
type Resolver interface {
	// Init initializes name resolver.
	Init(ctx context.Context, metadata Metadata) error
	// ResolveID resolves name to address.
	ResolveID(ctx context.Context, req ResolveRequest) (string, error)

	io.Closer
}

// ResolverMulti is an optional interface for name resolvers that can return multiple addresses.
type ResolverMulti interface {
	ResolveIDMulti(ctx context.Context, req ResolveRequest) (AddressList, error)
}

Kubernetes resolver 只用 DNS，不用 informer。 这是很多人会猜错的地方。在 components-contrib/nameresolution/ 全目录 grep EndpointSlice|informer|discoveryv1 结果是零匹配，kubernetes.go 也没有引入任何 client-go 依赖。它的 ResolveID 就是纯字符串拼接（kubernetes.go:96-102）：

func (k *resolver) ResolveID(ctx context.Context, req nameresolution.ResolveRequest) (string, error) {
	if k.tmpl != nil {
		return executeTemplateWithResolveRequest(k.tmpl, req)
	}
	// Dapr requires this formatting for Kubernetes services
	return req.ID + "-dapr." + req.Namespace + ".svc." + k.clusterDomain + ":" + strconv.Itoa(req.Port), nil
}

即 <appID>-dapr.<namespace>.svc.cluster.local:<internalGRPCPort>。

那个 -dapr 后缀的 Service 由 Dapr Operator 创建，而且是 headless service（pkg/operator/handlers/dapr_handler.go:160-162）：

func (h *DaprHandler) daprServiceName(appID string) string {
	return appID + "-dapr"
}

ClusterIP: "None" + 无 selector 负载均衡，意味着 DNS 查询直接返回所有 Pod IP。这正是 ResolveIDMulti 用 net.LookupIP 拿全部 A/AAAA 记录的意义所在，也是下一节 dns:/// 前缀能生效的前提。

mDNS resolver 则复杂得多（mdns/mdns.go，884 行），它用于自托管模式：

  • IPv4 / IPv6 双份独立缓存，各自独立 RWMutex、各自独立轮询
  • 地址 TTL 60 秒，惰性淘汰
  • 后台每 30 秒全量刷新
  • 用 SubscriberPool + sync.Once 做 single-flight：多个调用方同时请求同一个未缓存的 appID 时，只有第一个真正发起 browse，其余订阅结果
  • refreshChan 缓冲 36（注释说明：满了会阻塞发送方从而延迟服务调用，36 是避免过度分配的经验值）

resolver 的选择逻辑（pkg/runtime/runtime.go:1149-1159）：

if resolverName == "" {
	switch a.runtimeConfig.mode {
	case modes.KubernetesMode:
		resolverName = "kubernetes"

		resolverName = "mdns"

		...unable to determine name resolver for %s mode

}

注册通过构建标签控制（cmd/daprd/components/nameresolution_mdns.go）：

五、执行层：重试、重放与错误分类

5.1 invokeWithRetry

Invoke 先做方法名规范化，再判定本地/远端（direct_messaging.go:163-190）：

func (d *directMessaging) Invoke(ctx context.Context, targetAppID string, req *invokev1.InvokeMethodRequest) (*invokev1.InvokeMethodResponse, error) {
	// Normalize the method at the service invocation edge: reject forbidden
	// characters and resolve path traversal.
	if msg := req.Message(); msg != nil {
		normalized, normErr := method.NormalizeMethod(msg.GetMethod())
		if normErr != nil {
			return nil, status.Errorf(codes.InvalidArgument, "invalid method: %v", normErr)
		}
		msg.Method = normalized
	}

	app, err := d.getRemoteApp(ctx, targetAppID)
	if err != nil {
		return nil, err
	}

	// invoke external calls first if appID matches an httpEndpoint.Name or app.id == baseURL that is overwritten
	if d.isHTTPEndpoint(app.id) || strings.HasPrefix(app.id, "http://") || strings.HasPrefix(app.id, "https://") {
		return d.invokeWithRetry(ctx, retry.DefaultLinearRetryCount, retry.DefaultLinearBackoffInterval, app, d.invokeHTTPEndpoint, req)
	}

	if app.id == d.appID && app.namespace == d.namespace {
		return d.invokeLocal(ctx, req)
	}

	return d.invokeWithRetry(ctx, retry.DefaultLinearRetryCount, retry.DefaultLinearBackoffInterval, app, d.invokeRemote, req)
}

关于"本地 vs 远端"的判定，有个容易误解的点：判定依据是 app.id == d.appID && app.namespace == d.namespace，即 appID 与 namespace 同时相等，不是比较解析出来的地址是否等于自己。 hostAddress/hostName 字段只用于构造 X-Forwarded-For 等转发头。同 appID 的多实例场景下，每个实例都会判定为"本地"并直接走 app channel，不做网络往返——这是一个很自然的短路优化。

5.2 真实生效的重试策略

invokeWithRetry（direct_messaging.go:227-272）是重试的核心：

if !d.resiliency.PolicyDefined(app.id, resiliency.EndpointPolicy{}) && !req.IsStreamingRequest() {
	// Enable body buffering so the request can be replayed on retry.
	req.WithReplay(true)

	policyRunner := resiliency.NewRunnerWithOptions(ctx,
		d.resiliency.BuiltInPolicy(resiliency.BuiltInServiceRetries),
		resiliency.RunnerOpts[*invokev1.InvokeMethodResponse]{
			Disposer: resiliency.DisposerCloser[*invokev1.InvokeMethodResponse],
		},
	)
	return policyRunner(func(ctx context.Context) (*invokev1.InvokeMethodResponse, error) {
		attempt := resiliency.GetAttempt(ctx)
		rResp, teardown, rErr := fn(ctx, app.id, app.namespace, app.address, req)
		if rErr == nil {
			teardown(false)
			return rResp, nil
		}

		code := status.Code(rErr)
		if code == codes.Unavailable || code == codes.Unauthenticated {
			// Destroy the connection and force a re-connection on the next attempt
			// We also remove the resolved name from the cache
			teardown(true)
			if app.cacheKey != "" && d.resolverCache != nil {
				d.resolverCache.Delete(app.cacheKey)
			}
			return rResp, fmt.Errorf("failed to invoke target %s after %d retries. Error: %w", app.id, attempt-1, rErr)
		}

		teardown(false)
		return rResp, backoff.Permanent(rErr)
	})
}

一个必须指出的源码事实：invokeWithRetry 的形参 numRetries 和 backoffInterval 在函数体内完全未被使用（已 grep 验证，仅在签名第 229-230 行出现）。调用方传入的 retry.DefaultLinearRetryCount（3）和 retry.DefaultLinearBackoffInterval（1s）实际被忽略。

真正生效的是内建策略（pkg/resiliency/resiliency.go:340-351）：

func (r *Resiliency) addBuiltInPolicies() {
	// Cover retries for remote service invocation, but don't overwrite anything that is already present.
	if _, ok := r.retries[string(BuiltInServiceRetries)]; !ok {
		r.retries[string(BuiltInServiceRetries)] = &Retry{
			Config: retry.Config{
				Policy: retry.PolicyConstant,
				// Note: If this value changes to 0, don't forget to disable "Replay" in direct messaging
				MaxRetries: 3,
				Duration:   time.Second,
			},
		}
	}
}

即 Constant 策略、最多 3 次、固定间隔 1 秒，策略名 DaprBuiltInServiceRetries。数值上与死参数巧合一致，但这属于历史遗留而非设计。

两个触发"跳过内建重试"的条件：

  • 用户已定义 EndpointPolicy（PolicyDefined 为 true）→ 交给 API 层的 policyRunner 处理，避免双层重试叠加
  • 流式请求（IsStreamingRequest()）→ 无法重放，直接跳过

5.3 ReplayableRequest：重试的前提

这是整个重试机制最精巧的部分。问题很直接：请求体是 io.Reader（HTTP body），读一次就没了；重试意味着要再读一遍。

replayable_request.go:40-122 给出的方案是 T 型三通（tee）：

type replayableRequest struct {
	data             io.Reader
	replay           *bytes.Buffer
	lock             sync.Mutex
	currentTeeReader *streamutils.TeeReadCloser
	currentData      []byte
}

// RawData returns the stream body.
func (rr *replayableRequest) RawData() (r io.Reader) {
	rr.lock.Lock()
	defer rr.lock.Unlock()

	// If there's a previous TeeReadCloser, stop it so readers won't add more data into its replay buffer
	if rr.currentTeeReader != nil {
		_ = rr.currentTeeReader.Stop()
	}

	if rr.data == nil {
		r = bytes.NewReader(nil)
	} else if rr.replay != nil {
		l := rr.replay.Len()
		if rr.currentData == nil {
			rr.currentData = bsPool.Get(l)
		}
		rr.currentData = bsPool.Resize(rr.currentData, l)

		copy(rr.currentData[0:l], rr.replay.Bytes())
		rr.replay.Reset()

		// Create a new TeeReadCloser that reads from the previously-read data and then the data not yet processed
		mr := streamutils.NewMultiReaderCloser(bytes.NewReader(rr.currentData[0:l]), rr.data)
		rr.currentTeeReader = streamutils.NewTeeReadCloser(mr, rr.replay)
		r = rr.currentTeeReader
	} else {
		r = rr.data
	}
	return r
}

每次调 RawData() 时：先重放已读过的 currentData，再接上剩余未读的 rr.data，同时用 tee 把新读到的数据继续写入 replay 缓冲。缓冲区来自 sync.Pool（minByteSliceCapacity = 2 << 10）。

设计亮点：它不是"把整个 body 读进内存"，而是"边读边记，重放时拼接"。对未失败的请求，开销只是一次内存拷贝 + 一次 tee。而且如果数据本来就在内存中（HasMessageData()），WithReplay 直接是 no-op：

func (imr *InvokeMethodRequest) WithReplay(enabled bool) *InvokeMethodRequest {
	if imr.streamingRequest {
		return imr
	}
	// If the object has data in-memory, WithReplay is a nop
	if !imr.HasMessageData() {
		imr.SetReplay(enabled)
	}
	return imr
}

5.4 可重试错误的判定

只有两类 gRPC 状态码会被重试：codes.Unavailable 和 codes.Unauthenticated。

为什么是这两个？ 因为它们精确对应"目标实例已不存在"和"证书正在轮换"这两种瞬时故障：

  • Unavailable：目标 Pod 被调度走、正在启动、连接被服务端 GOAWAY
  • Unauthenticated：sidecar 证书轮换期间，对端用旧证书校验新连接会短暂失败

其余错误（如 InvalidArgument、PermissionDenied、NotFound）都是确定性的，重试一百次结果一样，所以立即 backoff.Permanent 终止。

这个分类体现了重试设计的核心原则：只对"重试可能成功"的失败重试。盲目重试所有错误在下游过载时会变成"重试风暴"，把可恢复的故障放大成雪崩。

Unavailable/Unauthenticated 时还会做两件额外的事——销毁连接并删除解析缓存：

teardown(true)
if app.cacheKey != "" && d.resolverCache != nil {
	d.resolverCache.Delete(app.cacheKey)
}

这构成了一个完整的自愈闭环：实例挂了 → 连接销毁 → 缓存失效 → 下次重新解析 → 拿到新实例地址。

5.5 流式请求的豁免

前面提到 ContentLength < 0 会调 SetStreamingRequest()。链式反应是：

  1. WithReplay 变成 no-op（不缓冲 body）
  2. invokeWithRetry 因 IsStreamingRequest() 跳过重试包装

这与官方文档一致：

“the request body is consumed as it is read and cannot be replayed.”

这是一个正确的取舍：为一个 1GB 的文件上传请求做重试，意味着要么缓存 1GB 到内存，要么放弃重试。Dapr 选择放弃重试，同时保证流式响应（SSE、文件下载）也能正常工作。而且熔断器等其他 resiliency 特性对流式请求依然生效。

5.6 关于超时：一个需要澄清的点

旧版文档提到"通过 gRPC 连接目标 sidecar 的超时时间为 5 秒"。在当前源码中并未找到服务调用级别的默认超时：全仓 grep remoteAppTimeout|daprRemoteAppTimeout|invocationTimeout|InvokeTimeout 无结果，pkg/messaging/ 中唯一的超时相关代码是 name resolution 的 backoff。

实际存在的超时只有：

  • 拨号超时 30 秒（pkg/api/grpc/manager/manager.go:45 dialTimeout）
  • 用户通过 Resiliency CRD 配置的 timeout（pkg/resiliency/policy.go:115-165 做 context.WithTimeout 包裹）

也就是说，默认情况下一次服务调用没有端到端超时保护，超时需要用户通过 Resiliency 策略显式配置。这是一个值得注意的运维风险点。

Manager（pkg/api/grpc/manager/manager.go:64-75）维护两个池：

远端池是 sync.Map，key 就是纯 address 字符串（host:port）：

func (p *RemoteConnectionPool) loadOrStoreItem(address string) *ConnectionPool {
	item, ok := p.pool.Load(address)
	if !ok {
		// Use LoadOrStore here in case another goroutine is in the exact same spot
		item, _ = p.pool.LoadOrStore(address, NewConnectionPool(maxConnIdle, 0))
	}
	return item.(*ConnectionPool)
}

单地址池内用引用计数近似"这条连接上并发了多少 RPC"（pool.go:121-146）：

const grpcMaxConcurrentStreams = 100

func (p *ConnectionPool) doShare() grpc.ClientConnInterface {
	for i := range len(p.connections) {
		// Check if the connection is still valid first
		if atomic.LoadInt32(&p.connections[i].referenceCount) == 0 && p.connections[i].Expired(p.maxConnIdle) {
			continue
		}
		count := atomic.AddInt32(&p.connections[i].referenceCount, 1)
		if count <= grpcMaxConcurrentStreams {
			return p.connections[i].conn
		}
		atomic.AddInt32(&p.connections[i].referenceCount, -1)
	}
	return nil
}

注意 grpcMaxConcurrentStreams = 100 不是 gRPC 真实的 stream 上限，而是 Dapr 自己维护的引用计数阈值（对齐 gRPC 服务端 HTTP/2 默认并发流数）。超过就新建一条连接。

Get 用两级锁 + double-check 避免并发重复建连（pool.go:52-83）：先读锁下 doShare()，失败后升级写锁再查一次，仍失败才 createFn()。

没有健康检查机制——只有基于时间戳的空闲淘汰（3 分钟）和一个每 45 秒跑一次的 StartCollector 清理协程。链路活性完全交给 gRPC keepalive。

dialPrefix 是关键（dial.go:22-31）：

	switch mode {
	case modes.KubernetesMode:
		return "dns:///"

dns:/// 前缀让 gRPC 接管 DNS 解析并启用客户端负载均衡，而不是让 Go 的 net.Dial 解析成单个 IP。配合前面 Operator 创建的 headless Service，DNS 返回多个 Pod IP，gRPC 的 round_robin 就能在它们之间分摊。

于是形成了两级负载均衡：

  2. gRPC round_robin：在 DNS 返回的多个 IP 间轮询（对 K8s headless service 有效）

另外注意：没有 WithBlock，dial 是 lazy 的，所以 createFn() 虽然持有写锁，但持锁时间很短。

6.3 mTLS 与 SPIFFE

mTLS 的注入只有一个点：g.sec.GRPCDialOptionMTLSUnknownTrustDomain(namespace, id)。

SPIFFE ID 格式（pkg/security/spiffe/spiffe.go:61-78）：

func FromStrings(td spiffeid.TrustDomain, namespace, appID string) (*Parsed, error) {
	...
	id, err := spiffeid.FromSegments(td, "ns", namespace, appID)
	...
}

即 spiffe://<trust-domain>/ns/<namespace>/<appID>。

服务调用用的是 UnknownTrustDomain 变体（security.go:366-387）：

// GRPCDialOptionMTLSUnknownTrustDomain returns a gRPC dial option which
// instruments client authentication using the current signed client
// certificate. Doesn't verify the servers trust domain, but does authorize the
// SPIFFE ID path.
// Used for clients which don't know the servers Trust Domain.
func (s *security) GRPCDialOptionMTLSUnknownTrustDomain(ns, appID string) grpc.DialOption {
	if !s.mtls {
		return grpc.WithTransportCredentials(insecure.NewCredentials())
	}

	expID := "/ns/" + ns + "/" + appID
	matcher := func(actual spiffeid.ID) error {
		if actual.Path() != expID {
			return fmt.Errorf("unexpected SPIFFE ID: %q", actual)
		}
		return nil
	}

	return grpc.WithTransportCredentials(
		grpccredentials.MTLSClientCredentials(s.spiffe.X509SVIDSource(), s.trustAnchors, tlsconfig.AdaptMatcher(matcher)),
	)
}

为什么叫 “UnknownTrustDomain”？ 因为在多集群/联邦场景下，调用方可能不知道目标 sidecar 属于哪个 trust domain。所以这里只校验 SPIFFE ID 的 path（/ns/<ns>/<appid>），不校验 trust domain。这是一个务实的取舍：牺牲了一部分跨信任域的隔离性，换取多集群部署的可行性。对控制面组件（Sentry、Operator、Placement）则用严格版本 GRPCDialOptionMTLS，用 tlsconfig.AuthorizeID 校验完整 ID。

证书来自 Sentry。sidecar 启动时用 TLS（非 mTLS，因为此时还没有自己的证书）+ token 向 Sentry 申请证书（pkg/security/sentry.go:76-131）：

conn, err := grpc.DialContext(ctx, //nolint:staticcheck
	sentryAddress,
	grpc.WithTransportCredentials(
		grpccredentials.TLSClientCredentials(trustAnchors, tlsconfig.AuthorizeID(sentryID)),
	),
	grpc.WithUnaryInterceptor(unaryClientInterceptor),
	grpc.WithReturnConnectionError(), //nolint:staticcheck
)
...
req := &sentryv1pb.SignCertificateRequest{
	CertificateSigningRequest: pem.EncodeToMemory(&pem.Block{
		Type: "CERTIFICATE REQUEST", Bytes: csrDER,
	}),
	Id:             sentryIdentifier,
	Token:          token,
	Namespace:      ns,
	TokenValidator: tokenValidator,
	JwtAudiences:   opts.JwtAudiences,
}

这个"先 TLS+token 换证书，再用证书做 mTLS"的引导过程，是零信任体系的经典模式：用已有的信任锚（trust anchors）验证 Sentry，用平台颁发的 token（K8s ServiceAccount 或自托管 token）证明自己的身份。

Sentry 服务端也在本仓库（pkg/sentry/server/ca/ca.go:257-285），它用同一个 spiffe.FromStrings(td, ns, appID) 构造证书，与客户端的 path 校验完全对齐。

6.4 teardown(destroy)：连接自愈

GetGRPCConnection 返回的第二个值是 teardown func(destroy bool)：

调用 效果
teardown(false) 引用计数 -1，归零时 MarkIdle()，连接保留复用
teardown(true) 立即 Close() 并从池中剔除，强制下次重建

destroy=true 只在一个地方触发——Unavailable/Unauthenticated 错误（direct_messaging.go:252-259）。这让故障连接能被快速淘汰，而不必等待 3 分钟的空闲超时。

7.2 ACL：身份来自证书，不是 header

这是本文最需要澄清的一个安全细节。

调用方会在 metadata 里写入 caller 身份（direct_messaging.go:559-569）：

func (d *directMessaging) addCallerAndCalleeAppIDHeaderToMetadata(callerNamespace, callerAppID, calleeAppID string, req *invokev1.InvokeMethodRequest) {
	req.Metadata()[invokev1.CallerNamespaceHeader] = &internalv1pb.ListStringValue{Values: []string{callerNamespace}}
	req.Metadata()[invokev1.CallerIDHeader] = &internalv1pb.ListStringValue{Values: []string{callerAppID}}
	req.Metadata()[invokev1.CalleeIDHeader] = &internalv1pb.ListStringValue{Values: []string{calleeAppID}}
}

但这些 header 不用于鉴权。 ACL 实际使用的是 mTLS 对端证书里的 SPIFFE ID（pkg/acl/acl.go:142-158）：

func ApplyAccessControlPolicies(ctx context.Context, operation string, httpVerb commonv1pb.HTTPExtension_Verb, isHTTP bool, acl *config.AccessControlList) (bool, string) {
	// Apply access control list filter
	spiffeID, ok, err := spiffe.FromGRPCContext(ctx)
	if err != nil {
		log.Debugf("failed to get SPIFFE ID from gRPC connection context: %v", err)
		return false, err.Error()
	}

	if !ok {
		// Apply the default action
		log.Debugf("Error while reading spiffe id from client cert. applying default global policy action")
	}

	action, actionPolicy := isOperationAllowedByAccessControlPolicy(spiffeID, operation, httpVerb, isHTTP, acl)
	emitACLMetrics(spiffeID, actionPolicy, action)
	...
}

而 spiffe.FromGRPCContext 读的是 grpccredentials.PeerIDFromContext(ctx)（spiffe.go:35-59），即 gRPC 从 TLS 握手结果中提取的对端证书身份。

这个区别至关重要：dapr-caller-app-id 是调用方自己填的，可以被伪造；SPIFFE ID 来自双向 TLS 握手，由 Sentry 签发的证书保证，无法伪造。Dapr 把 metadata 里的 caller ID 只用于 metrics 的 src_app_id 标签（见 callLocalRecordRequest），鉴权一律走证书身份。

由此推出一个重要的运维结论：关闭 mTLS 时，ACL 会失效。 因为 GRPCDialOptionMTLSUnknownTrustDomain 在 !s.mtls 时返回 insecure.NewCredentials()，服务端拿不到 peer ID，spiffeID 为 nil，ACL 直接回退到全局默认动作（acl.go:198-204）：

if spiffeID == nil {
	// Could not retrieve spiffe id or it is invalid. Apply global default action
	return isActionAllowed(action), actionPolicy
}

ACL 与 mTLS 是绑定关系，不是两个独立的安全特性。

7.3 方法名规范化：纵深防御

ACL 判定前会再做一次方法名规范化（daprinternal.go:391-422）：

// Used by CallLocal and CallLocalStream to check the request against the access control list.
// The method is normalized (forbidden characters rejected, path traversal resolved) as
// defense-in-depth before ACL evaluation. The normalized form is written back to the
// request so dispatch uses the same canonical string.
func (a *api) callLocalValidateACL(ctx context.Context, req *invokev1.InvokeMethodRequest) error {
	// Normalize method as defense-in-depth (caller should have already normalized).
	operation := req.Message().GetMethod()
	normalized, err := method.NormalizeMethod(operation)
	...
	if a.accessControlList != nil {
		var httpVerb commonv1pb.HTTPExtension_Verb //nolint:nosnakecase
		// Get the HTTP verb in case the application protocol is "http"
		appProtocolIsHTTP := a.AppConnectionConfig().Protocol.IsHTTP()
		if appProtocolIsHTTP && req.Metadata() != nil && len(req.Metadata()) > 0 {
			httpExt := req.Message().GetHttpExtension()
			if httpExt != nil {
				httpVerb = httpExt.GetVerb()
			}
		}
		callAllowed, errMsg := acl.ApplyAccessControlPolicies(ctx, operation, httpVerb, appProtocolIsHTTP, a.accessControlList)
		if !callAllowed {
			return status.Error(codes.PermissionDenied, errMsg)
		}
	}
	return nil
}

注意 // defense-in-depth (caller should have already normalized) 这句注释——方法名在发起侧已经规范化过一次（Invoke 开头），这里再规范一次。为什么要重复？因为 sidecar 可能被旧版本或恶意客户端直接调用，不能假设上游做过。这就是纵深防御（defense-in-depth）：跨越信任边界时，不信任任何上游的预处理结果。

NormalizeMethod（pkg/messaging/method/normalize.go）拒绝 #、?、空字节和控制字符，然后用 path.Clean 解析 ../ 路径穿越，最后处理 path.Clean 在相对路径下的边界情况。

ACL 匹配时会同时校验 trust domain 和 namespace（acl.go:213-220），并且操作名统一补 / 前缀后匹配，避免 /foo 与 foo 的不一致。

r := s.getRouter()          // CleanPathMiddleware, StripSlashesMiddleware
s.useMaxBodySize(r)         // 1. 请求体大小限制
s.useContextSetup(r)        // 2. 注入空的 EndpointCtxData
s.useTracing(r)             // 3. 链路追踪
s.useMetrics(r)             // 4. 指标
s.useCors(r)                // 5. CORS
s.useAPIAuthentication(r)   // 6. API Token 认证（必须在 CORS 之后）
s.useComponents(r)          // 7. 组件中间件（如 OAuth2）
s.useAPILogging(r)          // 8. API 日志
s.setupRoutes(r, s.api.APIEndpoints())

useContextSetup 排在 tracing/metrics 之前不是随意的——注释写得很清楚：

// Adds an empty `endpoints.EndpointCtxData` value to the context so it can be later set by the handler
// This context value is used by the logging, tracing, and metrics middlewares

handler 往这个容器里填数据，外层 middleware 在响应前读取。这是一种"反向数据流"：内层填充、外层消费，避免了 middleware 层需要理解每个 endpoint 的业务语义。

gRPC 侧的 server interceptor 链（pkg/api/grpc/server.go:281-335）则是：metadata 注入 → API allowlist → token 认证 → tracing → metrics → API logging。

十、设计亮点与可借鉴之处

通读整条链路，有几个决策值得在自己的系统里借鉴：

1. 用"内部统一表示"消化协议差异。
HTTP header 与 gRPC metadata 统一成 map[string]*ListStringValue，sidecar 间那一段完全不感知上游协议。这让"支持 N 种入口协议 × M 种出口协议"的成本从 N×M 降到 N+M。这是所有网关/代理类系统的通用范式。

2. 极窄的接口切断耦合。
DirectMessaging 只有一个方法。HTTP API、gRPC API、actors、proxy 四种上层都依赖它，四种下层实现（本地、远端、HTTP endpoint、gRPC proxy）都实现它。想加一种新入口或新后端，改动面都极小。

3. 用类型断言做向后兼容的能力升级。
ResolverMulti 是可选接口，老组件零改动继续工作，新组件实现后自动获得多地址 + 缓存能力。比给接口加方法（破坏所有实现）或加配置项（要写文档、要用户改配置）都优雅。

4. 重试只对"重试可能成功"的错误生效。
只重试 Unavailable 和 Unauthenticated，其余立即 backoff.Permanent。配合"销毁连接 + 删除解析缓存"形成自愈闭环。这是防止重试风暴的关键设计。

5. 跨越信任边界时重新校验，不信任上游。
方法名在发起侧规范化一次，在接收侧 ACL 判定前再规范化一次。注释明确写了 defense-in-depth。安全校验不能假设上游做过。

6. 鉴权身份必须来自密码学证据，不能来自可伪造的字段。
ACL 用 mTLS 证书里的 SPIFFE ID，而不是调用方自己填的 dapr-caller-app-id header。后者只用于 metrics。这个区分在很多自研系统里会被忽略，从而留下越权漏洞。

7. Handler 填数据、Middleware 消费数据的反向数据流。
handler 往 context 塞 SpanData，外层 middleware 在响应前读取用于 span 命名和日志。handler 不 import 任何 tracing 包，middleware 不理解任何业务语义。

8. 延迟决策：能不缓冲就不缓冲。
流式请求（ContentLength < 0）自动禁用重放和重试，用 io.Pipe 边收边转发。宁可放弃重试，也不把 1GB body 读进内存。

十二、总结

回到开头的五个问题，Dapr 的答案分别是：

问题 解法 关键实现
服务发现 可插拔 resolver + 分层缓存 nr.Resolver / ResolverMulti，20s TTL 缓存，组件内部各有策略
协议标准化 内部统一表示 Metadata + Message，两端按需转换
安全 mTLS + SPIFFE + ACL 证书身份做鉴权，纵深防御式方法名规范化
可靠性 精准重试 + 请求重放 + 连接自愈 仅重试 Unavailable/Unauthenticated，teardown(true) 淘汰故障连接
可观测 通用 middleware + endpoint 元数据 特定指标 + span 重命名，handler 与 tracing 解耦

如果只能记住一句话，那就是：Dapr 服务调用的本质，是把"应用间的远程调用"拆成"应用到 sidecar 的本地调用" + “sidecar 间的统一 gRPC 调用"两段，然后所有复杂性都集中在后一段的单一实现里。

这也是 sidecar 模式的核心价值——把 N×M 的集成问题，转化为 N+M 的适配问题。
