LangChain4j Java AI AI Services

LangChain4j 编程模型入门：用 AI Services 把大模型封装成 Java 接口

Posted by LiBaoxuan on Monday, July 6, 2026
9 分钟阅读

作为 Java 后端开发者，我们过去接入外部能力时，习惯把它封装成 SDK、Client、Repository 或 Service。但大模型进入业务系统后，问题会变得更复杂：它不只是一次 HTTP 调用，还涉及 Prompt、上下文、工具调用、知识检索、结构化输出和调用治理。

这篇文章聚焦 LangChain4j 的 AI Services 编程模型，尝试回答一个问题：如何用 Java 开发者熟悉的接口方式，把大模型能力封装成可维护的业务服务？

一、为什么 Java 后端需要 AI Services

如果只是做一个 Demo，我们当然可以直接调用模型厂商的 HTTP API：拼一段 Prompt，发送请求，拿到文本结果，然后展示给用户。但企业级 Java 应用很少停留在这个阶段。

一旦大模型能力进入 CRM、ERP、交付运营、采购审批或知识库问答系统，它就会遇到传统业务系统同样关心的问题：

  • 模型调用如何从业务代码中解耦？
  • 多轮对话的上下文如何管理？
  • 企业知识库如何参与回答？
  • 模型如何安全地调用内部系统能力？
  • 返回结果如何被业务层稳定消费？

这也是 LangChain4j AI Services 的价值所在。它不是只帮我们“请求一次大模型”，而是把模型、记忆、检索和工具调用这些能力组合起来，再通过一个 Java 接口暴露给业务代码。

换句话说，AI Services 解决的是工程边界问题：让业务系统调用 AI 能力时，不必到处拼 Prompt、解析响应、维护上下文，而是像调用一个普通 Java Service 一样调用大模型能力。

二、LangChain4j 的两个抽象层次

从课程材料的视角看，LangChain4j 大致运行在两个抽象层次上。

第一层是低层次抽象。开发者可以直接使用 ChatLanguageModel、UserMessage、AiMessage、EmbeddingStore、Embedding 等组件。这一层更接近 LangChain4j 的“原语”：控制力强，适合对调用过程做精细编排，但也意味着需要写更多胶水代码。

第二层是高层次抽象。开发者使用 AI Services 这类高级 API，把模型调用封装成声明式接口。框架隐藏了大量样板代码，同时仍然允许我们配置模型、记忆、检索器和工具调用。

如果说低层次 API 更像直接操作零件，那么 AI Services 更像把零件装配成一个可复用的业务模块。对大多数 Java 后端团队来说，后者更接近日常开发习惯：先定义接口，再由框架负责运行时实现。

三、AI Services：像 Feign / Spring Data JPA 一样调用大模型

课程里有一个很贴切的类比：Spring AI 的 ChatClient 更像 WebClient，走的是流式、链式的 Fluent API 风格；而 LangChain4j 的 AiServices 更像 Spring Data JPA 或 Feign，走的是声明式 API 风格。

这个差异非常关键。

使用 Fluent API 时，我们通常在代码中显式描述一次调用过程：设置系统提示词、拼接用户输入、配置参数、发起调用、解析结果。它直观、灵活，也适合需要临时编排的场景。

而声明式 API 的关注点不同。我们先定义一个 Java interface，用方法签名表达“我希望 AI 提供什么能力”，再通过注解、参数和构建器告诉框架如何完成模型调用。业务代码最终面对的是接口，而不是零散的 Prompt 组装逻辑。

这带来的好处是：AI 能力可以被纳入 Java 项目熟悉的分层结构中。Controller 调用 Service，Service 调用 AI Service；AI Service 背后再组合 ChatModel、Chat Memory、Retriever 和 Tools。这样一来，大模型能力就不再是散落在业务代码里的 API 调用，而成为一个有边界、有职责、可替换的工程组件。

四、一个 AI Service 由哪些部分组成

先看课程中的简化示例：

Assistant assistant = AiServices.builder(Assistant.class)
        .chatModel(CHAT_MODEL)
        .chatMemory(MessageWindowChatMemory.withMaxMessages(10))
        .contentRetriever(createContentRetriever(documents))
        .build();

这段代码可以拆成四个核心角色。

Assistant 是 AI Service 接口。它定义业务侧如何调用这项 AI 能力，例如“提问”“总结”“生成方案”或“处理运营请求”。接口本身像普通 Java Service，但运行时由 LangChain4j 生成实现。

chatModel 是模型接入层。它负责连接底层大模型，把消息发送给模型，并接收模型响应。对业务代码来说，模型供应商、请求参数、超时重试等细节应尽量收敛在这一层。

chatMemory 或 chatMemoryProvider 负责对话记忆。因为 LLM 本身是无状态的，每一次调用都不会天然记得上一轮说了什么。Chat Memory 的职责就是在调用模型前，把必要的历史消息重新放回上下文。

contentRetriever 负责检索增强。企业问答场景中，模型不能只依赖通用知识，还需要结合制度、SLA、采购规则、交付规范等内部文档。Retriever 会根据用户问题检索相关内容，再把结果提供给模型生成回答。

因此，AiServices.builder() 的意义不是简单创建对象，而是把模型、记忆、知识检索等能力组装成一个可被业务层调用的 AI 服务。

五、Chat Memory：让无状态模型具备上下文

在 LLM 应用里，“记忆”并不是模型真的把会话永久记在自己脑子里。更准确地说，应用在每次请求时选择一部分历史消息，连同当前问题一起发送给模型。Chat Memory 管理的就是这部分历史上下文。

课程中把 Chat Memory 分成三类思路。

第一类是窗口记忆，也就是 Sliding Window Memory。它按照消息数量保留最近 N 条对话。比如 MessageWindowChatMemory.withMaxMessages(10) 表示只保留最近 10 条消息。这种方式简单直接，适合 Demo、轻量客服、多轮问答等场景。

第二类是 Token 记忆，也就是 Token-based Memory。它不按消息条数裁剪，而是按 token 预算控制上下文长度。这样更贴近模型真实成本和上下文窗口限制，适合对成本、延迟和上下文长度更敏感的生产系统。

第三类是持久化记忆，也就是 Persistent Memory。它把会话历史保存到文件、数据库或外部存储中，让不同请求、不同服务实例之间可以共享或恢复上下文。企业系统通常还会在这一层考虑用户隔离、审计、数据清理和权限控制。

配套项目里的 EnterpriseChatMemoryProvider 就体现了这种工程化选择：

@Override
public ChatMemory get(Object memoryId) {
    String id = String.valueOf(memoryId);
    if (id.startsWith("token-") || id.contains("crm")) {
        return TokenWindowChatMemory.builder()
                .id(id)
                .maxTokens(900, tokenCountEstimator)
                .chatMemoryStore(memoryStore)
                .alwaysKeepSystemMessageFirst(true)
                .build();
    }
    if (id.startsWith("persist-") || id.contains("ops")) {
        return MessageWindowChatMemory.builder()
                .id(id)
                .maxMessages(24)
                .chatMemoryStore(memoryStore)
                .alwaysKeepSystemMessageFirst(true)
                .build();
    }
    return MessageWindowChatMemory.builder()
            .id(id)
            .maxMessages(10)
            .alwaysKeepSystemMessageFirst(true)
            .build();
}

这里不是用一个固定策略解决所有问题，而是根据会话标识选择不同记忆策略：CRM 场景偏 token 控制，运营场景偏持久化，普通场景则使用较轻量的窗口记忆。

这也给我们一个实践建议：生产系统里的 Chat Memory 往往不是“开或不开”的问题，而是如何组合短期窗口、token 裁剪和持久化存储，让上下文既够用，又不会失控。

六、Tools：让模型从聊天走向执行

如果没有工具调用，大模型更多是在“回答问题”：用户输入一段话，模型生成一段话。但企业应用通常不满足于聊天本身，它还希望 AI 能够查询客户信息、创建工单、检查库存、路由审批，甚至触发一段业务流程。

这就是 Tools 的价值。Tools 让模型可以在需要时调用外部 API、数据库查询或本地 Java 方法。对 Java 开发者来说，LangChain4j 的 @Tool 注解把这件事包装得很自然：我们把一个普通方法声明为工具，再用参数注解描述它需要什么输入。

配套项目中的 EnterpriseOperationTools 就是典型例子：

@Tool(name = "lookupCustomer", value = "查询客户画像、合同等级、健康度和客户成功负责人")
public CustomerSnapshot lookupCustomer(@P("客户编号，例如 C-1001") String customerId) {
    return dataService.customer(customerId);
}

@Tool(name = "createSupportTicket", value = "为企业客户创建售后或交付工单，并按优先级分派团队")
public Ticket createSupportTicket(
        @ToolMemoryId String memoryId,
        @P("客户编号") String customerId,
        @P("工单标题") String title,
        @P("问题描述") String description,
        @P("优先级：LOW/MEDIUM/HIGH/CRITICAL") String priority,
        @P("负责团队") String ownerTeam
) {
    Priority parsedPriority = Priority.valueOf(priority.toUpperCase(Locale.ROOT));
    String enrichedDescription = description + "；来源会话=" + memoryId;
    return dataService.createTicket(customerId, title, enrichedDescription, parsedPriority, ownerTeam);
}

这段代码背后的工程意义很重要：模型并不是随意操作系统，而是在我们暴露的工具边界内行动。工具名称、说明、参数类型和返回值共同构成了模型可调用能力的契约。

配套项目里的 OperationCopilot 则把这些工具挂到一个 AI Service 上：

return AiServices.builder(OperationCopilot.class)
        .chatModel(chatModel)
        .chatMemoryProvider(memoryProvider)
        .contentRetriever(retriever)
        .tools(tools)
        .maxSequentialToolsInvocations(3)
        .afterToolExecution(execution -> System.out.println("AI Tool executed: " + execution.request().name()))
        .build();

这样一来，用户可以用自然语言提出运营请求，而 AI Service 可以在模型判断后调用工具完成动作。比如查询客户画像、检查库存、创建支持工单或路由采购审批。

当然，Tools 也意味着更高的工程责任。真正进入生产环境时，我们需要考虑权限校验、参数验证、幂等控制、审计日志和人工确认机制。模型可以决定“调用哪个工具”，但业务系统必须决定“哪些工具可以被调用，以及调用后如何受控落地”。

七、企业问答 AI Service 示例

最后，我们用配套项目中的企业知识库助手，把前面的概念串起来。

先看 AI Service 接口：

public interface EnterpriseKnowledgeAssistant {

    @SystemMessage("""
            你是企业运营智能中台的知识库助手。
            回答必须结合检索到的企业制度、SLA、采购、交付、CRM 或安全规范。
            如果资料不足，请明确说明不确定，并给出下一步应找哪个部门确认。
            """)
    String ask(@MemoryId String conversationId, @UserMessage String question);
}

这个接口里有几个关键信息。

@SystemMessage 定义了助手的角色和回答边界：它不是泛泛聊天助手，而是企业运营智能中台的知识库助手。@MemoryId 标识当前会话，让 Chat Memory 可以按会话隔离上下文。@UserMessage 则标识用户当前输入的问题。

再看 Spring 配置中的组装方式：

@Bean
EnterpriseKnowledgeAssistant enterpriseKnowledgeAssistant(ChatModel chatModel,
                                                          EnterpriseChatMemoryProvider memoryProvider,
                                                          EnterpriseKnowledgeRetriever retriever) {
    return AiServices.builder(EnterpriseKnowledgeAssistant.class)
            .chatModel(chatModel)
            .chatMemoryProvider(memoryProvider)
            .contentRetriever(retriever)
            .storeRetrievedContentInChatMemory(true)
            .build();
}

这段代码把一个企业问答服务拆成了清晰的组件：

  • EnterpriseKnowledgeAssistant：业务侧调用的 AI Service 接口。
  • ChatModel：底层模型能力。
  • EnterpriseChatMemoryProvider：按会话提供记忆策略。
  • EnterpriseKnowledgeRetriever：从企业知识库检索相关制度和规范。
  • storeRetrievedContentInChatMemory(true)：把检索到的内容也纳入会话记忆，便于后续对话延续上下文。

完整链路可以理解为：

用户问题
  -> EnterpriseKnowledgeAssistant.ask(...)
  -> 根据 conversationId 取得 Chat Memory
  -> EnterpriseKnowledgeRetriever 检索企业知识
  -> ChatModel 结合系统提示词、历史上下文和检索内容生成回答
  -> 返回业务层

这里最值得注意的是边界设计。企业问答不是把用户问题直接丢给模型，而是让问题经过 AI Service 接口、记忆管理、知识检索和模型调用之后，再以业务服务的形式返回结果。这样做的好处是职责清晰：业务层不关心 Prompt 如何拼接，模型层不关心 Controller 如何暴露接口，检索层也可以独立演进。

八、小结

回到开头的问题：Java 后端为什么需要 LangChain4j AI Services？

我的理解是，它把大模型调用从“外部 API 请求”推进到了“接口驱动的业务能力”。这对企业应用非常关键。因为业务系统真正需要的不是一次孤立的模型回答，而是一个可以被 Controller、Service、Workflow 稳定调用的 AI 能力边界。

这篇文章重点拆了三个核心点：

  • AI Services 用声明式接口封装模型调用，让业务代码面对 Java interface，而不是散落的 Prompt 逻辑。
  • Chat Memory 解决上下文管理问题，让无状态模型在应用层获得多轮对话能力。
  • Tools 和 Retriever 让模型能够连接业务系统和企业知识库，从“会回答”进一步走向“能执行、能结合内部知识回答”。

对 Java 团队来说，LangChain4j 的吸引力就在这里：它没有要求我们完全跳出原有工程体系，而是把 AI 能力放回熟悉的 interface、annotation、Bean 和 Service 结构中。只要边界设计得当，大模型就可以成为企业系统中的一个可治理组件，而不是一段难以维护的调用脚本。

后续如果继续深入，可以沿着两个方向学习：一是结构化输出，把模型结果稳定映射为 Java DTO；二是更完整的 RAG 与 Agent 编排，把知识检索、工具调用、评估和治理串成生产级闭环。
