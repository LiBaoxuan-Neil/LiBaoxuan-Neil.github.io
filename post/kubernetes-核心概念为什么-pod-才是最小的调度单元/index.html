Kubernetes Pod 云原生 调度

Kubernetes 核心概念：为什么 Pod 才是最小的调度单元

Posted by LiBaoxuan on Wednesday, September 2, 2026
15 分钟阅读

系列 / Kubernetes 核心概念

刚接触 Kubernetes 的人，几乎都会卡在同一个地方：

容器已经是一个完整的封装单元了，为什么 Kubernetes 还要在它上面再包一层 Pod？而且这层 Pod 还看不到任何实体进程。

这个问题值得认真回答，因为它直接决定了你怎么写 YAML、怎么排障、怎么理解调度。这篇文章就从"容器到底是什么"开始，一路讲到调度器内部的两阶段流程和线上真正会踩的坑。

一、先回到容器本身：它到底是什么

很多人的心智模型里，容器是"轻量级的虚拟机"。这个比喻方便，但它是错的，而且会一路误导你对 Pod 的理解。

容器不是虚拟机，容器本质上就是宿主机上的一个进程。 只不过这个进程被三种内核机制包装过：

  • Namespace：做"视图隔离"。让这个进程以为自己独享 PID、网络、挂载点、主机名等资源。不同的 namespace 决定了你能"看到"什么。
  • Cgroups：做"资源限制"。限制这个进程能吃多少 CPU、内存、IO。
  • rootfs / 镜像分层：做"文件系统隔离"。让这个进程看到的是镜像里的文件，而不是宿主机的文件。

注意这个模型的隐含结论：一个容器，本质上是一个"进程视角"的东西。

这就带来了一个现实矛盾。真实的业务应用很少是单进程的，它通常长这样：

一个典型的 Web 应用节点，实际需要跑在一起的东西：
├── app           主业务进程（Java / Go / Node）
├── log-agent     采集 stdout 与业务日志，推送到 ES / Loki
├── config-sync   监听配置中心，热更新本地配置文件
├── proxy         服务网格数据面（Envoy / Linkerd proxy）
└── local-cache   本地缓存或 Unix Domain Socket 代理

这些进程之间存在一种**“超亲密关系”**（Kubernetes 官方的说法是 intimate relationship）：

  1. 它们必须调度到同一台机器上，否则一切免谈；
  2. 它们需要通过 localhost 或 Unix Domain Socket 通信，走网络栈的开销不可接受；
  3. 它们需要共享某些目录（比如日志目录、配置文件目录）；
  4. 它们需要一起生、一起死，生命周期必须严格对齐。

如果调度单元是容器，那调度器会把这 5 个进程当成 5 个独立个体，各自挑节点——超亲密关系当场崩塌。log-agent 跑在节点 A，app 跑在节点 B，日志采集直接失效。

Pod 就是为了解决这个问题而生的抽象。

二、Pod 是什么：一台"逻辑主机"

Pod 不是一个真实存在的进程，它是 Kubernetes 的原子调度单位：一组（一个或多个）共享上下文的容器的组合体。

一个更好用的心智模型是：

传统世界Kubernetes 世界
物理机 / 虚拟机Pod
机器上跑的进程组Pod 里的容器

所以那句经典说法是这么来的：“Pod 是一台逻辑主机，容器是这台主机上的进程。”

2.1 Pod 是怎么做到"共享"的：pause 容器

这是最关键、也最少被讲清楚的一环。

Kubernetes 并不直接创建你的业务容器。它先创建一个特殊的沙箱容器，也就是常说的 pause 容器（infra container / sandbox）。这个容器做的事情极其简单——拉取一个几百 KB 的极简镜像，然后执行一段代码，让进程永远 pause() 住。

它的唯一职责是：抢先占住 Pod 的 Network namespace 和 UTS namespace，然后什么都不干。

节点上实际发生的事情：

  Pod Sandbox (pause)
  ├── 持有 net ns  ←───────────┐
  ├── 持有 uts ns              │ setns 加入同一个 namespace
  └── PID 1                    │
                               │
  ┌──────────────┬─────────────┴──┬──────────────┐
  │  container   │   container    │  container   │
  │    app       │   log-agent    │    proxy     │
  └──────────────┴────────────────┴──────────────┘
         ↑                ↑               ↑
         └──── 共享同一个 Pod IP 与端口空间 ────┘

后续创建的业务容器，不是自己新建 namespace，而是通过 setns() 加入 pause 容器已经持有的那套 namespace。

这就解释了很多现象：

  • 为什么 Pod 里的内容器能共享同一个 IP？ 因为它们在同一个 net namespace 里。
  • 为什么容器之间能用 localhost 互通？ 因为 loopback 网卡在共享的 net namespace 里。
  • 为什么同一个 Pod 里两个容器不能绑定同一个端口？ 因为它们共享同一个端口空间，冲突是真冲突，不是"隔离了所以看不见"。
  • 为什么容器 CrashRestart 之后 Pod IP 不变？ 因为 net namespace 由 pause 容器持有，业务容器挂了 namespace 还在。

pause 容器还有第二个作用：当开启 shareProcessNamespace: true 时，它作为 PID 1 承担回收僵尸进程的职责。

2.2 Pod 内到底共享了什么，没共享什么

这是面试和排障的高频考点，也是写多容器 Pod 时最容易想当然的地方：

维度默认行为说明
Network namespace✅ 共享同一个 Pod IP、同一个端口空间、localhost 互通
UTS namespace✅ 共享同一个 hostname，容器里 hostname 命令结果一致
Volume✅ 通过声明共享每个容器各自把同一个卷挂载到自己 mount namespace 的不同路径
Mount namespace❌ 隔离每个容器有自己的根文件系统和镜像只读层，文件互不可见
PID namespace❌ 隔离（默认）默认互相 ps 不到；spec.shareProcessNamespace: true 可打开
IPC namespace⚠️ 依赖运行时行为不保证，跨容器共享内存请显式用 emptyDir + medium: Memory

这里有个非常常见的误区：以为 Pod 里容器共享文件系统。 不共享。它们只是可以把同一个 Volume 挂到各自不同的路径上：

apiVersion: v1
kind: Pod
metadata:
  name: web-with-log-agent
spec:
  volumes:
    - name: app-logs
      emptyDir:
        sizeLimit: 1Gi   # 生产环境务必设置，否则可能打爆节点磁盘触发 DiskPressure
    - name: shared-cache
      emptyDir:
        medium: Memory   # tmpfs，用于跨容器共享内存
        sizeLimit: 256Mi

  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: app-logs
          mountPath: /var/log/app      # 应用写日志到这里
        - name: shared-cache
          mountPath: /dev/shm/cache

    - name: log-agent
      image: fluent-bit:3.2
      volumeMounts:
        - name: app-logs
          mountPath: /data/log         # 采集器从"另一个路径"读到同一份数据
          readOnly: true

注意 mountPath 不同但底层是同一个目录——这才是 Pod 内文件共享的正确理解方式。

2.3 一个最小可用的 Pod

apiVersion: v1
kind: Pod
metadata:
  name: nginx-minimal
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          cpu: 500m
          memory: 256Mi

但请注意：生产环境几乎不要直接创建裸 Pod，原因见第六节。

三、Pod 的生命周期：相位、状态与优雅终止

3.1 相位 Phase：一个"很粗的摘要"

Pod 有 5 个相位，但它们的粒度非常粗，排障时几乎不能只靠 phase：

Phase含义什么时候出现
Pending已被接受，但还没跑起来正在调度 / 正在拉镜像 / PVC 未绑定
Running已绑定到节点，至少有一个容器在跑不代表服务可用！可能 readiness 还没过
Succeeded所有容器成功终止，且不会再重启Job / CronJob 正常完成
Failed至少一个容器以非 0 状态终止，且不会再重启Job 失败、容器启动即崩
Unknown拿不到 Pod 状态通常是 kubelet 与 API Server 通信异常，或节点失联

关键提醒：Running ≠ 可用。 容器起来了但 readinessProbe 一直失败，Pod 依然是 Running，却一个流量都接不到。真正排障要看 Conditions 和容器状态。

3.2 真正该看的是 Conditions

kubectl describe pod <pod-name>

重点关注这几种 condition：

  • PodScheduled：调度器是否成功给它找到了节点。为 False 且 reason: Unschedulable 就是调度失败。
  • Initialized：所有 init 容器是否执行完毕。
  • ContainersReady：所有业务容器是否就绪。
  • Ready：Pod 是否可以接流量（= ContainersReady + readiness 探针通过）。

3.3 重启策略 restartPolicy

spec:
  restartPolicy: Always    # 默认，Always / OnFailure / Never
  • Always：默认。容器无论以什么状态退出都重启。注意它由 kubelet 负责，重启是在原节点上原地重启，不是重新调度。
  • OnFailure：只有非 0 退出才重启。Job 场景常用。
  • Never：从不重启。

这里有个容易忽略的点：restartPolicy 是 Pod 级别的，对 Pod 内所有容器生效，而且不能给单个容器单独设置（原生 Sidecar 是唯一的例外情况）。

3.4 优雅终止的完整时序

这是线上 502 的头号来源，值得逐帧拆开看：

1. 用户执行 kubectl delete pod / Deployment 滚动更新
        ↓
2. API Server 设置 metadata.deletionTimestamp
   + deletionGracePeriodSeconds（默认 30s）
        ↓  ← 从这里开始，Pod 进入 Terminating
3. kubelet watch 到变更，开始关闭流程
        ↓
4. 执行 preStop hook（在容器内同步执行，有超时）
        ↓
5. 向容器主进程（PID 1）发送 SIGTERM
        ↓
6. 等待进程自行退出
        ↓
7. 宽限期耗尽 → 发送 SIGKILL 强杀

坑在哪？ 第 2 步之后，kubelet 关容器和 Endpoint Controller 摘除 Endpoint、kube-proxy 更新转发规则是并行异步的。也就是说：Pod 里的进程已经开始关了，但上游负载均衡器的规则可能还没更新完，新请求照样打进来 → Connection refused / 502。

标准解法是在 preStop 里睡几秒，等规则扩散完成：

spec:
  terminationGracePeriodSeconds: 45   # 总宽限期要 > preStop sleep + 应用退出时间
  containers:
    - name: app
      image: myapp:1.0
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]

四、Pod 是怎么被调度到节点上的

这是本文的核心。理解这套流程，你就能看懂 90% 的 Pending 问题。

4.1 全链路时序：谁做了什么

kubectl apply
    ↓
API Server：认证 → 鉴权 → 准入控制（Mutating → Validating）
    ↓
写入 etcd（此时 spec.nodeName 为空）
    ↓
┌───────────────────────────────────────────────┐
│ kube-scheduler 通过 Informer watch 到         │
│ 所有 nodeName == "" 的 Pod                    │
│                                               │
│   调度周期（Scheduling Cycle）                 │
│     QueueSort → PreFilter → Filter            │
│     → PostFilter → PreScore → Score           │
│     → NormalizeScore → Reserve → Permit       │
│                                               │
│   绑定周期（Binding Cycle）                    │
│     PreBind → Bind → PostBind                 │
└───────────────────────────────────────────────┘
    ↓  唯一动作：给 Pod 的 spec.nodeName 赋值
目标节点 kubelet watch 到"属于我的 Pod"
    ↓
CRI RunPodSandbox → 创建 pause 容器
    ↓
拉取镜像 → 创建 init / sidecar 容器 → 创建业务容器
    ↓
kubelet 上报 status → 更新 Pod 状态

最关键的一句话：调度器从来不去节点上启动任何东西。 它从头到尾只做一件事——给 Pod 写 spec.nodeName。剩下的全部交给 kubelet。这种"调度器只做决策、kubelet 只做执行"的切分，是 Kubernetes 控制面能水平扩展的根本原因。

4.2 调度周期：Filter 先筛，Score 再排

调度周期是串行的（一次只处理一个 Pod），分为筛选和打分两阶段：

第一阶段：Filter（硬约束，一票否决）

把不合适的节点直接淘汰。常见过滤项：

  • NodeResourcesFit：节点 allocatable - 已分配 requests 是否放得下这个 Pod（只看 requests，不看 limits）
  • NodeAffinity：nodeSelector 和 nodeAffinity.requiredDuringScheduling 是否匹配
  • TaintToleration：节点污点是否被 Pod 的 toleration 容忍
  • NodePorts / hostPort 是否冲突
  • VolumeBinding：PVC 的拓扑约束（比如某块云盘只能挂载在特定可用区的节点）
  • PodTopologySpread 的硬约束部分

全部节点都被淘汰时，进入 PostFilter，默认实现是抢占（Preemption）：尝试驱逐低优先级 Pod 腾地方。

第二阶段：Score（软偏好，择优录取）

给存活下来的候选节点打 0~100 分，取最高分。常见打分插件：

  • NodeResourcesBalancedAllocation：CPU / 内存分配比例是否均衡
  • NodeResourcesFit 的 LeastAllocated 策略：优先选资源剩余多的节点（装箱更松散）
  • ImageLocality：节点上是否已有镜像（省去拉取时间）
  • InterPodAffinity：Pod 间亲和 / 反亲和的软偏好
  • PodTopologySpread：跨 zone / 跨节点打散程度

然后是 Reserve（预订节点资源，防止并发调度超卖）→ Permit（批准 / 延迟 / 拒绝，gang scheduling 用这里）。

4.3 绑定周期：真正落子

Bind 阶段把 nodeName 写回 API Server。这一步是并发执行的，可以配置多个 goroutine 并行绑定。

4.4 一个反直觉的现象

调度失败的 Pod 不会立刻重试，而是被放进 UnschedulableQ 队列，进入指数退避。只有当集群状态发生变化（新增节点、其他 Pod 被删除释放了资源、PVC 绑定成功）时，它才会被重新挪回 ActiveQ 尝试调度。

这就是为什么有时你会看到：“Pod Pending 卡了很久没人管，突然就好了”——因为别的 Pod 释放了资源，触发了重新入队。

五、你写的 YAML 字段，如何悄悄改变调度结果

5.1 requests 是调度依据，limits 是运行时上限

这是最重要也最常搞混的一条：

  • 调度器只看 requests，完全不看 limits。
  • requests 决定 Pod 能被调度到哪（记账用的"预定"）
  • limits 决定 Pod 运行时被 Cgroups 卡多紧（实际使用的"天花板"）

一个隐蔽的坑：只写 limits 不写 requests 时，Kubernetes 会自动把 requests 设置成等于 limits（通过 LimitRange 的默认值或准入控制器）。结果就是你的 Pod 被当成"实打实要吃这么多资源"来调度，节点利用率直接崩。

5.2 三个 QoS 等级：决定了内存紧张时谁先死

QoS 等级判定条件节点资源紧张时的待遇
Guaranteed每个容器都设置了 CPU/内存的 requests 且 requests == limits最后才被驱逐，稳定性最高
Burstable至少一个容器设置了 requests 或 limits，但不满足 Guaranteed中间档，按"超出 requests 的程度"排序淘汰
BestEffort所有容器都没设置任何 requests / limits第一个被 OOMKill
# Guaranteed：每个容器、每种资源的 requests 都严格等于 limits
resources:
  requests:
    cpu: "1"
    memory: 1Gi
  limits:
    cpu: "1"
    memory: 1Gi

实践建议： 核心在线服务用 Guaranteed；离线任务、批处理用 BestEffort 或 Burstable。

关于 CPU limits 有一个进阶话题：CPU 是可压缩资源，超限时会被 CFS 配额节流（throttling），表现为 P99 延迟尖刺而不是直接报错。对延迟敏感的在线服务，业界有"不设 CPU limits、只设 requests"的做法；但完全不设也有风险，需要结合 cpuset 绑核或 CPU Burst 一起用。

5.3 亲和性、污点与拓扑打散

spec:
  # 节点亲和：优先（软）调度到 SSD 节点，但必须（硬）在 amd64 架构
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: kubernetes.io/arch
                operator: In
                values: ["amd64"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: node.kubernetes.io/disk-type
                operator: In
                values: ["ssd"]

    # Pod 反亲和：尽量不和同类服务挤在同一节点
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: myapp
            topologyKey: kubernetes.io/hostname
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"

注意 K8s API 命名里那串很长的后缀：

  • ...DuringScheduling...：调度时生效
  • ...IgnoredDuringExecution... / ...RequiredDuringExecution：运行时是否重新检查（目前亲和性基本都是 Ignored，即节点标签变了也不会驱逐已运行的 Pod）

5.4 拓扑打散：比反亲和更好用

topologySpreadConstraints 是反亲和的现代替代品，能精确控制"每个可用区最多几个副本"：

spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule      # 硬约束；ScheduleAnyway 为软约束
      labelSelector:
        matchLabels:
          app: myapp

5.5 优先级、抢占与 PDB

  • PriorityClass：数值越大优先级越高。资源不足时，高优先级 Pod 可以抢占（驱逐）低优先级 Pod。
  • PodDisruptionBudget（PDB）：注意它只保护自愿中断（如节点排空、kubectl drain、滚动更新），不保护硬件故障、OOMKill 这类非自愿中断。
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  minAvailable: 2          # 或 maxUnavailable: 1
  selector:
    matchLabels:
      app: myapp

六、工程实践：Pod 的几个高频陷阱

1. 裸 Pod 没有自愈能力，永远用控制器管理

直接 kubectl run 或 apply 一个裸 Pod，节点宕机后它不会被重新调度到其他节点，Pod 直接消失。生产环境请用 Deployment / StatefulSet / DaemonSet / Job。

顺带一提，DaemonSet 的 Pod 由 DaemonSet Controller 直接指定 nodeName，绕过了调度器（调度器只看 nodeName 为空的 Pod）。新版本里它通常用调度器的 PreBind 或 affinity 方案处理。

2. Pod 的大多数字段是不可变的

Pod 创建后，spec.containers[*].image、spec.containers[*].resources（旧版本）、spec.nodeName、spec.volumes 等大量字段不可修改。直接 kubectl edit 会报错。正确做法是改 Deployment 让它滚动更新重建 Pod。

唯一值得记住的例外：从 Kubernetes 1.27 起，InPlacePodVerticalScaling 特性允许在一定条件下原地修改 CPU / 内存 resources 而不重启容器（Alpha 阶段，到 1.33 已进入 Beta 并默认开启）。这是 VPA 原地更新模式的基础。

3. init 容器与原生 Sidecar

常规 init 容器：按顺序执行、跑完即退出、全部成功后业务容器才启动。适合做依赖检查、数据预热、配置拉取。

原生 Sidecar 容器（KEP-753）：写法是给 init 容器加上 restartPolicy: Always。

spec:
  initContainers:
    - name: logging-sidecar
      image: fluent-bit:3.2
      restartPolicy: Always          # 关键：标记为原生 Sidecar
      startupProbe:                  # 主容器会等它就绪后才启动
        httpGet:
          path: /health
          port: 2020
        periodSeconds: 2
        failureThreshold: 30
  containers:
    - name: app
      image: myapp:1.0

它解决了三个长期存在的痛点：

  1. 启动顺序确定：Sidecar 的 startupProbe 通过之后，主容器才开始启动。不用再在应用里写 wait_for_proxy.sh。
  2. 终止顺序确定：Pod 进入 Terminating 时，主容器先退出，Sidecar 最后才被终止。不会再出现"主容器还在发最后一批请求，Envoy 已经被杀了"的经典故障。
  3. Job 不再卡死：主容器退出后 Sidecar 自动清理，Pod 正常进入 Succeeded。以前 Job 里跑日志 Sidecar 会永远卡在 Running。

版本情况：1.28 Alpha → 1.29 Beta（默认开启）→ 1.33 GA（正式稳定，无法关闭）。

4. 三种探针的职责不要混淆

探针作用失败后果
startupProbe慢启动保护，成功前 liveness 不生效重启容器
readinessProbe是否可以接流量从 Service Endpoint 摘除（不重启）
livenessProbe是否还活着（死锁检测）重启容器

最重要的一条纪律：livenessProbe 绝不能依赖外部依赖。数据库抖动时，如果 liveness 探针检查 DB 连接，会导致全集群 Pod 同时被重启，把一次小故障放大成雪崩。外部依赖只能放进 readinessProbe。

5. 退出码速查表

排障时 kubectl describe pod 看 Last State 的 Exit Code：

退出码含义常见原因
0正常退出Job 完成 / 预期内的终止
1 / 2应用自身错误代码异常、配置错误
125 / 126 / 127容器运行时错误127 = 找不到命令，通常是 command / args 写错或镜像里没有该二进制
137被 SIGKILL 杀掉OOMKilled（内存超 limits）或宽限期到了被强杀
143收到 SIGTERM正常的优雅终止

6. 排障命令速查

# 调度失败：看 Events，Reason=FailedScheduling 会直接告诉你原因
kubectl describe pod <pod> | grep -A 20 Events

# 查看 Pod 没被调度成功的真实原因（资源不足 / 污点 / 亲和性）
kubectl get events --field-selector reason=FailedScheduling --sort-by=.lastTimestamp

# 为什么这个 Pod 在这个节点：看调度器打分明细（需要开启调度器日志）
kubectl describe pod <pod> | grep -i "node:"

# 快速看 Pod 卡在哪个 Condition
kubectl get pod <pod> -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'

七、小结：Pod 的心智模型

把这篇文章压缩成三句话：

  1. 容器是进程，Pod 是主机，控制器是运维机器人。 Pod 把"必须在一起的一组进程"打包成一个不可分割的调度原子，用一个 pause 容器锚定共享的 namespace，用 Volume 打通文件共享，用统一的控制面保证生命周期对齐。

  2. 调度器只做一件事：给 Pod 选一个节点并写 nodeName。 先 Filter 硬筛、再 Score 软排，选不出来就走抢占。剩下的创建、拉镜像、重启、上报状态全是 kubelet 的活。

  3. Pod 是"牲畜"不是"宠物"。 它随时可能被重建，IP 会变，节点会换。任何需要在 Pod 之间保持稳定寻址的东西，都应该交给 Service、Ingress 或者服务网格，而不是把 IP 写进配置。

理解了 Pod 为什么存在，你写的每一份 YAML 都会变得更合理——因为你知道每个字段最终是在跟调度器、kubelet 还是内核对话。
