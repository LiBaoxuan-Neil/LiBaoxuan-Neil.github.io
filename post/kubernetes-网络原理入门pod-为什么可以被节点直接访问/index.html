Kubernetes 网络原理入门：Pod 为什么可以被节点直接访问

从网络命名空间、veth、网桥到 CNI 和 Service

Posted by LiBaoxuan on Tuesday, September 8, 2026

刚接触 Kubernetes 网络时，一个看起来很神奇的现象是：在 Kubernetes 节点上，直接执行下面的命令，就能访问某个 Pod：

curl 10.42.0.43

这个地址既不是节点的 IP，也不是 Service 的 ClusterIP，而是 Pod IP。为什么节点可以直接访问一个看起来位于“容器内部”的地址？Pod 的网卡到底在哪里？veth、网桥、路由和 CNI 又分别做了什么？

本文不从复杂的网络插件源码讲起，而是先建立一个适合初学者的心智模型，再把一次 HTTP 请求的完整路径串起来。

一、先给出结论

Kubernetes 的 Pod 网络并不是一套脱离操作系统的魔法。它主要利用 Linux 内核提供的几种能力：

  • 网络命名空间（Network Namespace）：隔离每个 Pod 看到的网卡、IP、路由和端口。
  • veth pair：一对虚拟网卡，像一根连接 Pod 和节点的虚拟网线。
  • Linux 网桥（Bridge）：节点内部的虚拟交换机，连接多个 Pod。
  • 路由和转发：决定数据包应该从哪个接口发出、送往哪个 Pod 或节点。
  • CNI（Container Network Interface）：在 Pod 创建和删除时，负责把网络设备、IP 和路由配置好。

因此可以把整件事浓缩成一句话：

Pod 是被网络命名空间隔离出来的网络空间；veth 把 Pod 接入节点；CNI 再通过网桥、路由或隧道，让节点和其他 Pod 能够找到它。

你的 curl 能成功，是因为命令在 Kubernetes 节点上执行，而该节点已经具备访问 Pod 网段的网络路径。

二、从 Linux 的网络命名空间开始

2.1 网络命名空间是什么

Linux 的网络命名空间可以理解为一套独立的网络视图。每个网络命名空间拥有自己的：

  • 网络接口，例如 eth0、lo；
  • IP 地址；
  • 路由表；
  • 端口空间；
  • 部分网络协议栈状态和防火墙规则。

普通 Linux 主机只有一个主要的网络命名空间。运行容器时，容器运行时可以为容器创建一个新的网络命名空间，让容器中的进程看到一套与宿主机不同的网络环境。

这就是“隔离”的来源：容器里的 localhost 指向容器所在的网络命名空间，而不是节点的 localhost。

2.2 为什么两个环境都能使用 80 端口

假设节点上已经有一个程序监听节点网络命名空间的 80 端口，同时某个 Pod 内的 nginx 监听 Pod 网络命名空间的 80 端口，这两个监听通常不会冲突。

原因不是它们使用了不同的数字端口，而是它们属于不同的网络命名空间，拥有不同的端口空间。

但同一个 Pod 中的多个容器默认共享网络命名空间。因此，如果同一个 Pod 内的两个容器都尝试监听 0.0.0.0:80，就会发生真正的端口冲突。

2.3 Pod 和容器在网络上的关系

Kubernetes 的 Pod 通常包含一个或多个容器，但一个 Pod 只拥有一个 Pod 网络身份：

  • 一个 Pod IP；
  • 一个网络命名空间；
  • 一个端口空间。

同一个 Pod 内的容器可以通过 localhost 互相访问。例如，主容器可以访问 sidecar 容器提供的 localhost:15000 服务。

不同 Pod 通常拥有不同的网络命名空间和不同的 Pod IP。它们不能直接使用对方的 localhost，而应使用对方的 Pod IP、Service 名称或其他服务发现方式。

三、veth pair：连接 Pod 与节点的虚拟网线

3.1 veth 是什么

veth 是 virtual Ethernet 的缩写。它总是成对创建：

veth pair
┌──────────────┐                 ┌──────────────┐
│  Pod 一端     │ <--------------> │  节点一端     │
│  eth0         │    虚拟网线      │  vethxxxx     │
└──────────────┘                 └──────────────┘

veth pair 的特性很简单：从一端发出的数据包，会从另一端出现。

创建 Pod 网络时，CNI 通常会完成类似的动作：

  1. 创建一对 veth；
  2. 把一端放入 Pod 的网络命名空间；
  3. 把 Pod 内的一端命名为 eth0；
  4. 把节点内的另一端接入网桥或其他转发设备；
  5. 给 Pod 的 eth0 配置 Pod IP；
  6. 在 Pod 内配置默认路由。

所以，Pod 里的 eth0 并不是一块真实的物理网卡，而是 veth pair 的一端。

3.2 一次从 Pod 发出的数据

假设 Pod A 的 IP 是 10.42.0.43，它访问 Pod B 的 IP 10.42.0.42：

Pod A 的 eth0
      │
      │ veth pair
      ▼
节点上的 vethxxxx
      │
      │ 网桥转发或节点路由
      ▼
节点上的另一个 vethyyyy
      │
      │ veth pair
      ▼
Pod B 的 eth0

如果两个 Pod 位于同一个节点上，数据通常可以在节点内部完成转发，不需要经过物理网卡。

四、Linux 网桥：节点内部的虚拟交换机

4.1 网桥的基本作用

Linux 网桥可以把它想象成一台软件实现的二层交换机：

  • 每个 veth 可以看成交换机上的一个端口；
  • 多个 Pod 通过各自的 veth 接入网桥；
  • 网桥根据 MAC 地址学习和转发以太网帧。

简化后的节点内部结构如下：

                 节点网络命名空间

 Pod A                     Pod B
10.42.0.43                10.42.0.42
   │ eth0                    │ eth0
   │                         │
 veth-a                    veth-b
   │                         │
   └──────────┬──────────────┘
              ▼
        Linux 网桥
       （虚拟交换机）

在同一节点上，Pod 之间的通信可能直接经过网桥，也可能由 CNI 使用其他内核转发机制完成。具体实现取决于 CNI 插件和网络模式，但“Pod 通过虚拟接口接入节点，再由节点转发”的整体模型是一样的。

4.2 网桥和路由不是同一个东西

这两个概念经常混在一起：

  • 网桥主要解决二层转发，类似交换机，依据 MAC 地址转发帧。
  • 路由主要解决三层转发，依据目标 IP 和路由表选择出口。

简单理解：

网桥：这个以太网帧应该从哪个端口出去？
路由：去这个 IP 网段，应该走哪个网络接口或下一跳？

在实际 CNI 中，两者可能同时存在，也可能主要使用三层路由、隧道或 eBPF 等机制。初学时不必把所有插件实现强行归结为“只有网桥”。

五、CNI：负责把 Pod 网络配置出来

5.1 CNI 是规范，不是单一插件

CNI 的全称是 Container Network Interface。它定义了容器运行时与网络插件之间如何协作。

当 kubelet 请求容器运行时创建 Pod 沙箱时，运行时会调用 CNI 插件。CNI 插件负责：

  • 创建或配置网络接口；
  • 将接口放入 Pod 的网络命名空间；
  • 分配 Pod IP；
  • 配置 Pod 内的路由；
  • 配置节点侧的路由、网桥、隧道或转发规则；
  • Pod 删除时清理这些资源。

所以 CNI 更像一套“网络插件接口标准”，而不是某一个固定的软件。

常见的 CNI 或网络方案包括：

  • Flannel：常用于提供 Pod 网络连通；
  • Calico：既能提供网络连通，也擅长 NetworkPolicy；
  • Cilium：使用 eBPF 提供网络、策略和可观测性能力；
  • Canal：通常可以理解为 Flannel 与 Calico 的组合。

RKE2 的具体 CNI 取决于安装配置。不要仅凭 RKE2 这个发行版名称就断定当前集群一定使用某一种插件，实际情况可以查看集群配置和运行中的 DaemonSet。

5.2 为什么每个节点都需要 CNI 组件

CNI 通常以 DaemonSet 的形式在每个节点上运行，因为每个节点都要负责本地 Pod 的网络配置，并可能参与跨节点转发。

可以查看网络相关组件：

kubectl get pods -A -o wide

也可以搜索名称中包含网络插件的 Pod：

kubectl get pods -A | grep -Ei 'calico|flannel|canal|cilium|weave'

六、Pod CIDR：Pod 地址从哪里来

6.1 Pod 网段和 Service 网段

Kubernetes 集群通常会规划不同用途的地址段：

地址段 用途 示例
Pod CIDR 分配给 Pod 10.42.0.0/16
Service CIDR 分配给 Service 虚拟地址 10.43.0.0/16
Node 网段 分配给节点或物理网络 例如 192.168.1.0/24

Pod IP 和 Service ClusterIP 都是集群虚拟网络中的地址，但二者用途不同：

  • Pod IP 标识具体的 Pod 实例；
  • Service IP 标识一组后端 Pod 的稳定服务入口。

6.2 Pod CIDR 通常会按节点切分

为了让各节点管理自己的 Pod 地址，集群可能把大的 Pod 网段分配为多个节点子网：

集群 Pod CIDR：10.42.0.0/16

节点 A：10.42.0.0/24
节点 B：10.42.1.0/24
节点 C：10.42.2.0/24

在截图中，两个 nginx Pod 的 IP 是：

10.42.0.42
10.42.0.43

它们都显示运行在 rke2-single 节点上，因此很可能都属于该节点负责的 Pod 子网。最终仍应以实际路由表和 CNI 配置为准。

查看 Pod 所在节点和 IP：

kubectl get pods -n k8s-demo -o wide

查看节点的 Pod CIDR：

kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.podCIDR}{"\n"}{end}'

七、为什么节点能直接 curl Pod IP

现在回到最开始的命令：

curl 10.42.0.43

假设命令是在 rke2-single 节点上执行的，完整过程可以拆成以下步骤：

第一步：curl 创建 TCP 连接

curl 默认访问 HTTP 的 80 端口，因此目标是：

目标 IP：10.42.0.43
目标端口：80

节点上的进程先把目标 IP 交给节点内核网络栈。

第二步：节点查询路由表

节点内核会查询路由表，判断 10.42.0.43 应该从哪个接口发出：

ip route get 10.42.0.43

如果结果显示该地址通过某个 CNI 接口、网桥或本地路由可达，就说明节点知道如何把数据包送过去。

第三步：数据包进入 CNI 网络

数据包根据路由进入节点侧的 CNI 网络设备。对于同节点 Pod，可能经过：

节点路由 → 网桥 → veth → Pod eth0

对于跨节点 Pod，则可能经过：

节点路由 → CNI 跨节点转发 → 另一节点 → veth → Pod eth0

跨节点转发的具体方式可能是 VXLAN、host-gw、BGP、eBPF 或其他实现，不能只用一种方式概括所有集群。

第四步：nginx 监听 80 端口

Pod 网络命名空间内的 nginx 进程监听 80 端口，收到请求后返回默认 HTML 页面。

因此，节点能够访问 Pod IP，并不是因为 Docker 或 Kubernetes 自动做了一个“宿主机端口映射”，而是因为节点本身就是 Pod 网络的一部分，CNI 已经配置了到 Pod 网段的路径。

八、containerPort: 80 到底做了什么

Deployment 中的配置是：

ports:
  - containerPort: 80

这个字段很容易和 Docker 的端口映射混淆，但它们不是一回事。

8.1 containerPort 不是端口映射

Docker 中的端口映射通常类似：

docker run -p 8080:80 nginx

它表达的是：

宿主机 8080 → 容器 80

而 Kubernetes 的 containerPort 主要是对容器端口的声明和元数据描述：

containerPort: 80

它通常不会：

  • 自动开放节点端口；
  • 自动创建 Service；
  • 自动完成宿主机端口到 Pod 端口的映射；
  • 让 nginx 开始监听 80 端口。

真正监听端口的是容器里的应用进程，也就是 nginx。

8.2 Service 如何引用这个端口

Service 可以把自己的 port 转发到后端 Pod 的 targetPort：

apiVersion: v1
kind: Service
metadata:
  name: my-nginx
spec:
  selector:
    run: my-nginx
  ports:
    - name: http
      port: 80
      targetPort: 80

这里的关系是：

访问 Service:80
       ↓
转发到某个 Pod:80

targetPort: 80 可以写成数字，也可以引用容器端口名称。把端口名称写出来通常更清晰：

containers:
  - name: my-nginx
    image: nginx:latest
    ports:
      - name: http
        containerPort: 80

然后 Service 使用：

targetPort: http

九、Service 解决的不是“Pod 能不能通信”

9.1 直接访问 Pod IP 的问题

虽然节点或其他 Pod 可能可以直接访问 Pod IP，但不建议把 Pod IP 写死在业务配置里，原因有两个：

  1. Pod IP 不稳定：Pod 被删除、重建、滚动更新后，新的 Pod 可能获得不同的 IP。
  2. Pod IP 不代表服务：Deployment 有多个副本时，每个副本都有自己的 IP，客户端需要自己选择目标并处理故障。

9.2 Service 提供稳定入口

Service 通过 selector 找到匹配的 Pod，并维护后端端点：

客户端
  │
  ▼
Service: my-nginx
  │
  ├── Pod 10.42.0.42:80
  └── Pod 10.42.0.43:80

客户端只需要访问 Service 的 DNS 名称：

curl http://my-nginx

跨命名空间时可以使用完整的 DNS 名称：

curl http://my-nginx.k8s-demo.svc.cluster.local

Service 通常提供：

  • 稳定的虚拟 IP；
  • 稳定的 DNS 名称；
  • 后端 Pod 的自动发现；
  • 多副本之间的流量分配；
  • Pod 就绪状态变化时的端点更新。

查看 Service 后端：

kubectl get endpoints my-nginx -n k8s-demo

在较新的 Kubernetes 版本中，也可以查看 EndpointSlice：

kubectl get endpointslice -n k8s-demo

9.3 Service 的访问范围

默认类型 ClusterIP 的 Service 主要用于集群内部访问。要从集群外部访问，可以根据场景使用：

  • NodePort：在节点上暴露一个端口；
  • LoadBalancer：请求云平台或基础设施提供外部负载均衡；
  • Ingress：以 HTTP/HTTPS 规则统一对外提供入口；
  • Gateway API：更现代、更结构化的流量入口模型；
  • kubectl port-forward：适合临时调试，不适合作为生产入口。

十、为什么集群外的电脑通常不能 curl Pod IP

Pod IP 通常属于集群内部的虚拟地址空间，例如：

10.42.0.0/16

你的个人电脑通常没有到这个网段的路由。即使你知道 Pod IP，也不代表网络路径存在。

不同位置的访问情况大致如下：

发起位置 直接访问 Pod IP 主要原因
Pod 所在节点 通常可以 节点有 CNI 路由和转发能力
其他 Kubernetes 节点 通常可以 CNI 提供跨节点 Pod 网络
集群内其他 Pod 通常可以 Pod 网络设计要求 Pod 之间可达
集群外部电脑 通常不可以 没有 Pod 网段路由或隧道
公网客户端 通常不可以 Pod IP 不是公网服务地址

这里的“通常”很重要，因为 NetworkPolicy、防火墙、云网络 ACL、CNI 配置和路由模式都可能改变实际结果。

十一、用几条命令观察真实网络

11.1 确认 Pod 的 IP 和节点

kubectl get pod -n k8s-demo -o wide

重点关注：

  • IP：Pod IP；
  • NODE：Pod 所在节点；
  • NOMINATED NODE：调度抢占相关信息，通常为空。

11.2 查看节点如何到达 Pod IP

ip route get 10.42.0.43

这条命令比单纯查看完整路由表更适合入门，因为它直接回答：

去 10.42.0.43 的数据包会从哪里走？

11.3 查看节点路由表

ip route

可以重点寻找包含 Pod 网段的路由，例如：

10.42.0.0/24 dev cni0

或：

10.42.0.0/24 via <某个节点地址> dev flannel.1

实际接口名称会因 CNI 和网络模式不同而变化。

11.4 查看网桥和链路

ip link show type bridge

bridge link

在某些集群中也可能看到类似 cni0、flannel.1、vxlan.calico 等接口，但不能假定所有环境都存在完全相同的名称。

11.5 查看 HTTP 连接细节

curl -v http://10.42.0.43

-v 会显示 DNS、TCP 连接、HTTP 请求和响应头等信息。可以用它区分：

  • 网络不通；
  • 端口不通；
  • HTTP 服务返回错误；
  • nginx 正常返回页面。

11.6 从 Pod 内部测试

kubectl exec -n k8s-demo -it <pod-name> -- sh

进入 Pod 后测试另一个 Pod：

curl http://10.42.0.42

如果镜像没有 curl，可以尝试 wget，或者临时启动一个网络诊断 Pod。

十二、把整个模型串成一张图

                         集群内部网络

  节点 Shell
  curl 10.42.0.43
        │
        ▼
  节点路由表：目标属于 Pod 网段
        │
        ▼
  CNI 转发层
  网桥 / 路由 / 隧道 / eBPF
        │
        ├────────────── 同节点 ──────────────┐
        │                                    │
        ▼                                    ▼
  veth pair                            veth pair
        │                                    │

        │                                    │
        └──────── nginx 监听 80 端口 ────────┘

  Service 不在这条“直接访问 Pod IP”的路径上。
  Service 是为稳定寻址、端点发现和多副本流量分配提供的另一层抽象。

十三、初学者最容易混淆的几个概念

1. Pod IP 和 Service IP 不一样

Pod IP 指向一个具体的 Pod；Service IP 指向一组后端 Pod 的服务入口。

2. containerPort 和端口映射不一样

containerPort 是端口声明，不等于宿主机端口开放，也不等于 docker -p。

3. 节点能访问 Pod IP，不代表公网能访问

节点拥有 Pod 网段路由，公网客户端通常没有。可达性取决于网络路径，而不是只取决于 IP 看起来是否正确。

4. CNI 不是只有网桥

CNI 可能使用网桥、路由、VXLAN、BGP、eBPF 等机制。网桥是一个很好的入门模型，但不是所有集群的完整实现。

5. Pod IP 不适合写死

Pod 可以被重建，IP 会变化。需要稳定访问时使用 Service DNS，而不是把某个 Pod IP 固定写入配置。

十四、总结：记住这五句话

  1. 容器本质上是被 Linux 内核隔离机制包装的进程。
  2. 网络命名空间为 Pod 提供独立的网卡、IP、路由和端口空间。
  3. veth pair 把 Pod 网络命名空间连接到节点网络命名空间。
  4. CNI 负责分配 Pod IP，并配置网桥、路由、隧道或其他转发机制。
  5. 节点可以 curl Pod IP，是因为节点有到 Pod 网段的网络路径；Service 的作用是稳定入口和负载均衡，而不是让 Pod 网络从无到有。

当你再次看到类似下面的命令时：

curl 10.42.0.43

可以按这个顺序思考：

目标 IP 属于哪个网段？
        ↓
当前环境有没有到这个网段的路由？
        ↓
数据包会经过哪个 CNI 接口或下一跳？
        ↓
目标 Pod 是否在监听对应端口？
        ↓
是否有 NetworkPolicy、防火墙或安全组拦截？
